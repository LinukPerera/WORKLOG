## LogPrompts Research (Alpha-Log-Probs) — OpenAI API compatibility research — 4 hours (11:30–15:30)

Source: `Alpha-Log-Probs/worklog.md`

Got an OpenAI API key today. Before using it, catalogued every approach documented across this
project's source material (not just the plain teacher-forced `mean_logprob` this study already
tested) and checked which are even possible via OpenAI's current API: QE mode (teacher-forced),
candidate ranking, MT mode (generation-time confidence), the LLM-as-judge Yes/No approach from
`LOGPROBS_Shindan.md` (the one that actually beat `mean_logprob` in Shindan's own prior numbers),
self-consistency/agreement, and the hybrid/calibration ideas in the vendored repo's
`CONTRIBUTING.md`.

**Finding, verified against OpenAI's own docs (not search-snippet hearsay, which was
contradictory and untrustworthy on model-specific details):** prompt-token/teacher-forced
logprobs are **not available via OpenAI's API at all, as of today** — the only mechanism that
ever existed for this (`echo` + `logprobs` on the legacy `/v1/completions` endpoint, three legacy
models) was shut down 2026-09-28, already past. This rules out this study's main approach (QE
mode) and candidate ranking via OpenAI categorically, not as a model-availability question but
a "the feature doesn't exist anymore" one. Generation-token logprobs (needed for MT mode and the
Yes/No judge) are available via Chat Completions on at least some models (OpenAI's own cookbook
demonstrates gpt-4/gpt-4o/gpt-4o-mini), but reasoning-tier models reportedly reject
logprobs/temperature outright — exactly which current model names fall into which bucket could
not be pinned down reliably from secondary sources, so this needs a direct empirical check
against the real API rather than more documentation reading.

Wrote up the full catalogue, sourcing, and verdict in `OPENAI_API_COMPATIBILITY.md`. No
`OPENAI_API_KEY` was set in the environment yet at that point — asked the user how they'd like
to provide it before running the empirical model check.

**Correction, after the user pointed specifically at the "QE demos" table in
`external/logprobs-mt-qe/README.md`**: read all seven demo scripts' actual source rather than
relying on the table's one-line descriptions. Found a mischaracterization of `agreement.py` —
its own docstring's live-usage recipe explicitly calls for re-scoring each generated sample via
`prompt_logprobs` (teacher-forced), not just comparing generated text, so as literally coded it
is blocked on OpenAI exactly like the other QE demos. The real distinction turned out to be
*what's being scored*, not *whether logprobs are involved*: `rank_candidates.py` scores fixed,
externally-authored candidates (teacher-forcing by definition, no way around it) while
`agreement.py` scores samples the model **itself just generated**, so each sample's own
generation-time logprobs (already returned by the generation call) can stand in for the
teacher-forced re-score without changing the result — an adaptation, not a reimplementation of
the 8-line `agreement_score()` formula. Updated `OPENAI_API_COMPATIBILITY.md` with a corrected
per-script table and this explanation.

**Also checked the README's second breakdown — the "Layer" table** (per-token logprobs,
per-token derived signals, aggregates, distributional summary, span detector, language-script
drift, candidate ranker, optional preset). Most layers exist in two implementations — one
generation-mode (`mt.lib_mt_confidence`), one QE-mode (`qe.lib_prompt_logprobs`) — and the split
holds exactly along those lines in every case: generation-mode layers work via OpenAI's Chat
Completions (same `choices[0].logprobs.content` shape), QE-mode layers don't. This surfaces a
structural fact the demos table alone didn't make obvious: **OpenAI's API cannot be used to
quality-score a translation it did not generate itself, for any signal in the whole stack** —
not a per-script limitation, a boundary of the provider. Added this breakdown and the structural
conclusion to `OPENAI_API_COMPATIBILITY.md`.

User then asked to explore all the ways to work with logprobs via this access. Wrote and ran
`scripts/openai_logprobs_exploration.py`, probing five more capabilities empirically: (A) `n>1`
samples + `logprobs=True` in one call — **works**, directly cutting Experiment 3's cost from N
calls to one; (B) the Responses API's `include=["message.output_text.logprobs"]` — accepted but
returns no logprobs, matching community reports of inconsistent support there, so staying on
Chat Completions is the right call; (C) `logit_bias` alongside `logprobs=True` — **works**, can
bias toward Yes/No tokens for judge robustness without forcing a wrong verdict (tested on the
wrong-translation case: still correctly answered "No" with the bias applied); (D) streaming +
`logprobs=True` together — **works**; (E) the legacy `/v1/completions` endpoint with
`echo`+`logprobs` — confirmed dead for this account (`404 model_not_found`, explicit deprecation
message), empirically closing the loop on what `OPENAI_API_COMPATIBILITY.md` had only confirmed
from the docs. Folded all five findings into that doc and updated `OPENAI_EXPERIMENTS_PLAN.md`'s
Experiment 1 and 3 designs accordingly. `gpt-4o` is now a confirmed working default model for
everything this project needs from OpenAI.
