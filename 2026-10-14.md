## LogPrompts Research (Alpha-Log-Probs) — judge pilot: 100 segments, models, and a calibration check that changed the recommendation — 1.5 hours (11:30–13:00)

Source: `Alpha-Log-Probs/worklog.md`

Started the day listing what's left: vLLM server had crashed overnight (not urgent since the
vLLM study is already complete), and none of the three planned OpenAI experiments were built
beyond smoke tests.

User set the pilot's scope directly: 100 well-picked sentences, a few models biggest to
smallest, save results so pilot-vs-scale is trackable later.

**Sample selection** (`scripts/select_judge_pilot_sample.py`): drew from the *same* 1,500
segments the vLLM study already scored, stratified by MQM severity (34 clean / 33 minor / 33
severe, deliberately not the natural ~80/20 base rate, for better small-N statistics) across 5
systems. Every pilot segment already had a real vLLM `mean_logprob` to compare against, on
identical text.

**Models** (checked the account's actual available-models list live rather than guessing):
tried `o4-mini`, `gpt-5`, `gpt-4.1`, `gpt-4o`, `gpt-4o-mini`. `gpt-5-chat-latest` was listed by
the models API but not actually servable (404, deprecated). Plain `gpt-5` and `o4-mini` both
failed with `403 You are not allowed to request logprobs from this model` — the reasoning-tier
restriction `OPENAI_API_COMPATIBILITY.md` predicted, now confirmed empirically.

Built `scripts/score_segments_openai_judge.py` (the real Experiment 1 scorer, `logit_bias` on
Yes/No tokens, token-usage tracking per call) and ran all 100 segments against the three working
models in 12–14 seconds each.

**Caught and fixed a real bug while writing the evaluation script**: first pass computed the
judge's AUC with `higher_is_bad=True` on `P(Yes)`, which is backwards — a high P(Yes) means the
model thinks the translation IS accurate, so it should correlate with LOWER bad-probability.
Fixed, cleared the tracking file, re-ran.

**Result, corrected**: all three working models clearly beat the vLLM teacher-forced result on
the *identical* 100 segments (0.650) — gpt-4o-mini 0.795, gpt-4.1 0.734, gpt-4o 0.724. All three
also land above Shindan's own internal LLM-judge baseline (0.57-0.72). The smallest, cheapest
model tested came out best, not the largest — flagged as a real finding to confirm at scale.
100% found-rate on every working model (vs. vLLM's own ~5% alignment-failure rate).

Wrote up the full results in `OPENAI_JUDGE_PILOT_RESULTS.md`. Built
`scripts/run_openai_judge_evaluation.py` to append a row per (model, run_label, date) to
`results/eval/openai_judge_tracking.tsv`.

**Recommendation written up**: scale Experiment 1 to the full 1,500-segment sample using
`gpt-4o-mini` as primary (cheapest and best in this pilot) with `gpt-4o` as a secondary check.
`gpt-5`/`o4-mini` confirmed not worth further debugging for this capability.

**User asked to also try a bigger/newer model.** Tried `gpt-6.1-sol`, `gpt-5.4`, and
`gpt-5.1-chat-latest`. The `-chat-latest` naming pattern does not avoid the reasoning
restriction — both `gpt-5-chat-latest` and `gpt-5.1-chat-latest` are listed but 404 as
deprecated. The other two surfaced three *more* distinct parameter incompatibilities: `max_tokens`
renamed to `max_completion_tokens` on the newest generations; `logit_bias` rejected outright on
`gpt-5.4`; `top_logprobs` capped at 5 (not 20) on `gpt-5.4`; and a reasoning model failing
because hidden reasoning tokens ate the entire budget before any visible answer.

Rather than hardcode a model-version cutoff that would go stale, rewrote the scoring call as
`_create_with_param_fallback()`: a loop that reads each new error message, applies the one
specific adaptation it describes, and retries. Applied this, `gpt-5.4` went from 0/100 scored to
100/100 after four automatic fallbacks fired in sequence. `gpt-6.1-sol` hit the first fallback
successfully, then failed on `logprobs` itself being unsupported — a genuine capability gap, left
as a documented dead end.

**Result: `gpt-5.4` scored 0.725 AUC** — right in the middle of the four working models, not
ahead of `gpt-4o-mini`'s 0.795 despite being the newest generation and needing real extra
adaptation and reasoning-token cost to run at all. Second independent piece of evidence pointing
the same way. Updated `OPENAI_JUDGE_PILOT_RESULTS.md` accordingly.

**User raised a concern worth taking seriously: the four models' headline AUCs (0.724-0.795) are
"basically the same" — what does that mean?** Checked the real data: the raw `P(Yes)`
distribution is extremely bimodal (78-94% of values sit above 0.99 or below 0.01) — the judge
behaves far more like a near-binary classifier than a calibrated probability. More
consequential: splitting the headline AUC by MQM severity (clean-vs-severe "easy" cut vs.
clean-vs-minor "hard" cut) showed `gpt-4o-mini`'s headline win is almost entirely riding the easy
cases. On the hard cut — the one that actually matters for review triage — `gpt-4o-mini` is
barely better than a coin flip (0.595) and is the worst of the four there, while `gpt-4.1`
(0.706) is clearly the best. vLLM's own `mean_logprob` is literally worse than chance (0.464) on
the hard cut, so the judge approach is still a real improvement over vLLM either way.

**This reverses the model recommendation from earlier today.** Rewrote
`scripts/run_openai_judge_evaluation.py` to compute severity-stratified AUC and a P(Yes)
bimodality share as standard, tracked output — regenerated `results/eval/openai_judge_tracking.tsv`
with the richer schema for all four models. Rewrote `OPENAI_JUDGE_PILOT_RESULTS.md`'s
recommendation: **scale Experiment 1 with `gpt-4.1` as primary, not `gpt-4o-mini`** — it's the
only model that holds up on both the easy and the hard cut, with `gpt-4o-mini` kept only as a
cheap secondary comparison. Flagged honestly that each stratified AUC here rests on only ~62-67
segments — the direction is trustworthy, the exact gap is not. Updated
`OPENAI_EXPERIMENTS_PLAN.md`'s Experiment 1 status to match.

**What's left now**: scale Experiment 1 to the full 1,500-segment sample with `gpt-4.1` primary
and `gpt-4o-mini` as secondary, using the now-stratified evaluation pipeline throughout.
Experiments 2 and 3 remain lower priority, unchanged.

## Tikka translation process — S0101 live-run results, 6-metric quality comparison, cost accounting — 4.5 hours (15:00–19:30)

Source: `Tikka_translation_process/WORKLOG.MD`

Ran the S0101 four-provider live translation batch and compared the results.

**Combined results into one readable file per provider.** Each provider had 149 scattered
per-unit files; built `combine_results.py` to collapse each into a single
`combined_results/<provider>.txt` — parsed `<answer>` content only (not the raw API response),
in strict unit order, with Kimi's 10 gaps shown explicitly (`[NO RESULT - ...]` + reason) rather
than silently missing.

**Built a 6-metric comparison against the current translation (`analyze_results.py`).** Compares
each provider's output to the hidden `reference_translation` ground truth (never shown to any
model) across:
- Monolingual fluency: GPT-2 perplexity, Flesch readability indices, and an LLM (Claude Haiku)
  fluency score 1-10.
- Semantic divergence vs. the reference: sentence-embedding cosine similarity, word-level
  Levenshtein similarity, Jaccard token overlap.

Installed `textstat`, `rapidfuzz`, `torch` (CPU), `transformers`, `sentence-transformers` into
the Tikka venv for this. Validated on 5 units first (caught that LLM fluency scoring barely
discriminates between providers — 7s and 8s across the board, since all four are already
fluent — a real finding, not a bug) before running the full 149×4 batch (586 records; 10 fewer
than 596 — Kimi's known gaps).

**Findings** (full writeup: `analysis_report.md`, raw data: `analysis_records.json`/`.csv`):
fluency is close across all four and not very discriminating (LLM scores 7.05-7.41/10; GPT-2
perplexity favours Claude slightly but with large variance). Divergence from the existing
translation shows more real separation: **OpenAI (GPT-6 Astra) diverges most from the reference
on every divergence metric**; **Claude and Kimi are closest** (trading the lead across the three
metrics); **Meta sits in the middle** throughout. No provider wins on every metric. Caveats
recorded plainly in the report: Claude is both a candidate and the LLM judge (didn't score
itself highest); Flesch scores are unstable on short units (11/586 outliers, all 3-sentence
units); GPT-2 is a small 2019-era model, a relative signal only; Kimi's n=139 vs. the others'
149 isn't a perfectly fair comparison.

**Added the missing baseline — fluency had never been measured on the reference translation
itself.** Caught on review. Built `analyze_reference_fluency.py` (reuses `analyze_results.py`'s
tools) to run the same 3 monolingual fluency metrics on the current/production translation, 149
units. Result: the reference's perplexity (38.41) and LLM fluency score (7.23) both land
squarely inside the 4 candidates' range (36.43–39.42 and 7.05–7.41) — none of the AI
translations is more or less fluent than the one already in production. Readability sits in the
middle too, and the same short-unit Flesch instability affects the reference just as much as the
candidates (10/149 vs. 11/586 — consistent rate). `analysis_report.md` updated with this as the
headline fluency finding.

**Uploaded results to the repo.** `s0101_four_ai_results/` — the 4 combined per-provider
translation files and `analysis_report.md` — committed and pushed (only those 5 files; nothing
else from the experiment folder).

**Priced the analysis itself.** The LLM fluency-scoring step's token usage was never captured at
call time, so built `compute_analysis_cost.py` to reconstruct the exact same 735 prompts
(deterministic — same DB, same result files) and get real input-token counts via Anthropic's
free `count_tokens`. Real cost: **$0.1983** (183,596 real input tokens + ~2,940 estimated output
tokens, Claude Haiku 4.5 at $1.00/$5.00 per MTok) — negligible next to the $54.39 spent
generating the translations themselves. Added to `analysis_report.md` as a new "Cost of this
analysis" section.

**Clarified: also wanted the per-provider translation-generation costs in the analysis file
itself**, not just the analysis step's own cost. Added a "Cost per provider" table (Claude
$13.47/149, OpenAI $20.07/149, Kimi $20.54/139, Meta $0.31/149 — from `live_run_report.md`) plus
cost-per-usable-unit, read against the quality results: **Meta is both the cheapest by nearly two
orders of magnitude and mid-pack on every quality metric** — the standout on cost-adjusted
value; Kimi is the most expensive per usable unit despite also being the only one with gaps.

**Day closed.** S0101 four-provider experiment is now fully documented end to end: mapper table
→ leak-free test dataset → dry run → live run → combined results → quality analysis → cost
accounting, all pushed to the repo or recorded here.
