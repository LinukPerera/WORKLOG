## PaliVerse RAG — Azure budget limits confirmed, start/stop cost discipline, multi-consumer schema migration applied — 4.5 hours (15:30–20:00)

Source: `mini_rag/WORKLOG.MD`, referred to here as "PaliVerse RAG"

Two asks: understand the real Azure limits, design the framework around them, check
cost-effectiveness, and confirm full compliance with the nonprofit credit's terms; separately,
whether idle cost can be avoided, and making sure the DB/RAG/vector-store/metadata design works
as one shared point for every consumer (info-tab generation, a future live Q&A feature,
internal benchmarking), not something built single-purpose.

**Real Azure limits, confirmed from Microsoft's own docs, not guessed**:
- The nonprofit grant is **$2,000 USD/year, fixed, non-negotiable**. Doesn't roll over —
  unused balance is forfeited at year-end. Renewal isn't automatic.
- The subscription has no hard spending cap — exceeding $2,000 silently converts to
  pay-as-you-go against the billing profile's card. Not a terms risk, a financial one that has
  to be self-policed.
- Exact remaining balance / expiration date is **not accessible via the CLI** for this
  subscription type — confirmed via Microsoft's own docs that it's Portal/Nonprofit-Hub-only.
  Flagged to the user to check directly.
- **Real spend breakdown** (Nov 1-3, via the cost management API): a small total, of which
  **91% is a pre-existing, unrelated VM and its backup vault** — this project's own Postgres
  server is a tiny fraction of that, mostly storage while stopped. Means the real budget
  available to this project is closer to ~$1,800/year than the full $2,000.

**Compliance confirmed in full**: the eligible-services list covers everything this project
runs or plans to run; nothing on the excluded or prohibited lists touches any of it. No
violation, no risk beyond the financial self-policing one above.

**Cost-effectiveness framework**: running the current server tier 24/7 would eat nearly the
whole remaining budget on Postgres alone — not viable. Since Flexible Server bills per
compute-hour while running (not a flat monthly fee), the fix is start/stop discipline around
actual work sessions rather than a different architecture: roughly 15-20 active hours/month
brings real cost down to **~$7-8/month** on the current tier. The still-unfiled Azure support
ticket for the cheaper Burstable tier remains worth pursuing in parallel, since it removes the
need for that discipline entirely once granted.

**Idle-cost question, answered**: Azure Flexible Server has no true serverless scale-to-zero —
only manual/scheduled stop, with a real ~2-5 minute cold start on resume (verified live today).
Genuinely instant scale-to-zero Postgres exists elsewhere in the market but isn't a first-party
Azure service, so it wouldn't be covered by the nonprofit credit at all. User confirmed fine
with scheduled/cold-start behaviour for now (still in testing, not live) — to revisit once the
live Q&A feature actually ships. Built and ran start/stop scripts to confirm the pattern works
end to end.

**Multi-purpose DB/RAG/vector/metadata design**: read the existing schema properly before
proposing anything new, and found it was already built for this — canonical/synthetic
separation, swappable embedding model/version per chunk, full citation/provenance, a knowledge
graph, glossary, query log. The existing 4-agent retrieval pipeline is already
consumer-agnostic — the future live Q&A feature and info-tab generation were always meant to
share one retrieval core, only the final generation step differs. So "one shared point" was
already the real design; it just needed two real gaps closed:
- A new `quality_status` column (verified/needs_review/superseded) on the chunk table —
  directly closing the long-open gap from two units generated with zero entity grounding
  earlier (once that benchmark is ingested, those rows get flagged needs_review instead of
  silently serving ungrounded content).
- A new `consumer_scope` column (internal/all) on the chunk table, so content can be held back
  from a future live user while staying usable internally, without a second table; and a new
  `consumer` column on the query log, so usage against the $2,000/year grant can be split by
  consumer instead of lumped together.

Applied live to the Azure server, verified directly against the live schema.
