## PaliVerse RAG — built and tested the first real MCP server, then revised the client email through three rounds of real feedback — 4 hours (10:30–14:30)

Source: `mini_rag/WORKLOG.MD`, referred to here as "PaliVerse RAG"

**Built the first real MCP server**, after being asked to prioritise it
ahead of sending the client update so the email could report real
working tools rather than a plan. Implemented all six tools the
client's own method request named by name: search by meaning, get a
passage by reference, get the linked commentary, find related
passages, collect the full evidence set for a question in one call
(their own "Step 1" - meaning search plus following the root/
commentary/sub-commentary link in both directions plus grouping
repeated stock formulas), and check quotations against the database
(the code half of their "Step 4").

**Found and fixed a real bug while testing, not after.** The query
embedding passed into the similarity search was a plain list, and the
database silently treated it as the wrong type instead of the vector
type it needed to be - the same class of bug found earlier this
project, just in a new piece of code. Fixed before trusting any result
from it.

**Tested all six tools against the real database before trusting any
of them**: the database-only tools first, then the two needing a live
embedding call, then the quotation-checker with a deliberately built
real-quote / false-quote / nonexistent-reference set to confirm it
actually tells them apart. Also checked the server itself answers a
real request over an actual network connection, not just by calling
the underlying code directly.

**Scoped deliberately**: this first version only does what's already
real and working today - no original-language retrieval yet, no
speaker-identification check, no AI half of the verification step -
matching the "don't re-engineer everything" instruction, and keeping
every call fast and free. Wrote up plainly what's real today versus
what still has to happen before the client's own Claude can actually
connect to it: hosting (needs a real cost check), a web address and
certificate (needs the client's decision), and access control (needs
the client's list of who gets in) - none of the three started yet,
deliberately, since each needs either a cost check or client input
first.

**Revised the client email through three genuine rounds of feedback,

## LogPrompts Research (Alpha-Log-Probs) — two pre-registered Shindan tests run (confusion, escalation-reliability), knowledge-base drafts rewritten — 4 hours (15:30–19:30)

Source: pulled from the `Alpha-Log-Probs` GitHub repo (`worklog.md`).

Aim: run the two tests pre-registered the day before on Shindan profile 17's flags — does
adding log-probabilities reduce the overlap between real and false flags, and does it make the
escalate-or-trust decision more reliable — and prepare the knowledge-base text.

**Built `scripts/p17_confusion_feasibility.py`** (plus `tests/test_p17_confusion_feasibility.py`,
3 tests) — the confusion-overlap test itself: fit on the cutoff half, read once on the test half,
AUC and overlap-coefficient with 1,000 cluster-bootstrap replicates and a Holm correction across
categories. One real correction made before running it: an earlier assumption that
category-level probability values didn't exist for unflagged rows turned out to be wrong —
confirmed they do exist, and the test's own pre-registration section was corrected to say so
before the run, not after seeing results.
- **Real result**: combining the log-probability signal with Shindan's own score improves AUC
  in all 5 categories tested (Meaning +0.044, Completeness +0.045, Grammar +0.076, Punctuation
  +0.099, Style +0.018) and the overlap coefficient between real and false flags drops by
  0.02-0.08 in every case (though it stays high overall, 0.76-0.87). **Proceed rule met**: 5 of
  5 categories improve, none got worse.

**Built `scripts/p17_escalation_reliability.py`** (plus 4 tests) — rules written first
(committed before any run), then the script, then one real run (35 seconds): for each category,
at escalation budgets of 10/20/30/40%, measures the share of still-trusted flags that are false,
the catch rate, Brier score, calibration error, how much budget it takes to cut the trusted
false-share by 5/10/15 points, behaviour specifically in Shindan's own uncertain zone, per
language pair, and a swap-replication check.
- **Real result**: at a 20% escalation budget, the trusted false-share drops slightly in every
  category tested (e.g. Completeness 0.842 → 0.832, Punctuation 0.748 → 0.736), and the lowest-
  confidence quarter of flags by the combined score catches real errors well above the random
  rate in all 5 categories. But **inconclusive by the pre-registered rule**: only 1 of 5
  categories passes every condition required, the real reduction tops out at 1.5 points against
  a 2-point threshold set in advance, though the direction of the effect is consistent across
  every category and held up under the swap-replication check too.

**Removed a draft request document** (for log-probabilities on Shindan's unflagged segments)
and reworded the knowledge-base drafts to follow the project's own documentation rules — no

**Drafted (not published) further knowledge-base content**: two tracker rows and an updated
