### Terminology-impact arm

Raised an important process question: real MT work often has to stick to a required
glossary/jargon, and the required term may not be the model's own most probable continuation —
so a logprob-based confidence signal could flag a *correct*, terminology-compliant translation
as low-confidence purely because the term was imposed. Before trusting the main study's signals
in any terminology-heavy domain, this needs to be measured. See `TERMINOLOGY_IMPACT.md` for the
full write-up. Summary of what was built (all public-data-only, all backend-independent to write
and unit-test):

- Found and verified a real public dataset built exactly for this: the WMT 2023 Terminology
  Shared Task data (`zouhar/wmt-terminology-2023` on Hugging Face). For the same source segment,
  it has real WMT23 participant-system outputs under `base` (unconstrained), `rand` (random
  term), and `term` (proper/required term enforced) conditions, plus the exact required-term
  hints. Noted the license is an unspecified Creative Commons variant on the dataset card;
  treating it as research/evaluation-only per standard WMT shared-task norms.
- Wrote `scripts/download_terminology_dataset.py` and downloaded the de-en slice: 2,948
  segments, 23,584 `base` rows, 23,584 `term` rows, flattened to one row per
  (segment, system, condition).
- Wrote `scripts/terminology_adapter.py` to locate a required term's exact token span inside a
  teacher-forced translation (handling the common case of *multiple* required terms per segment
  — caught and fixed a bug in an early draft that only looked at the first hint). Terms a system
  reworded/inflected away from the hint's surface form are dropped, not zero-filled.
- Wrote `scripts/evaluate_terminology.py` (`paired_summary()`: mean/median diff, share-lower,
  Wilcoxon signed-rank via `scipy.stats`) for two paired comparisons: forced-term tokens vs. the
  rest of the same sentence, and a `term` translation vs. its paired `base` translation for the
  same source+system.
- Wrote `scripts/score_terminology_impact.py` and `scripts/run_terminology_evaluation.py` (same
  `--base-url`/`--model` pattern as the main study) to run those comparisons at scale once a
  backend exists. Dry-validated the grouping/hint-extraction/term-location logic against the
  real downloaded de-en data (no backend needed for this part) — found a genuine real example
  (segment 0, system `DCU-TU-TR`) where the `term` condition correctly uses "treatment" /
  "cosmetic" and `base` uses "supply" / "aesthetic" for the same source, which is precisely the
  kind of case this analysis is built to measure.
- 21/21 `pytest tests/` pass without any live backend (added `test_terminology_adapter.py`,
  `test_evaluate_terminology.py`).

## LogPrompts Research (Alpha-Log-Probs) — backend chosen and built: vLLM, CPU-only — 5 hours (16:30–21:30)

Source: `Alpha-Log-Probs/worklog.md`

The one remaining blocker for both study arms. Checked actual hardware first rather than
guessing: 8 vCPU Xeon Silver 4314 (Ice Lake-SP, full AVX-512 incl. AVX512_VNNI), 31GB RAM,
43GB free disk, **no GPU**. Ruled out llama.cpp (confirmed open upstream bug,
`ggml-org/llama.cpp#27174`: `echo+logprobs` silently returns zero prompt-token logprobs — would
break the entire teacher-forced QE pipeline) and Ollama (already flagged flaky for this in the
vendored repo's own README). Decided on vLLM, the only backend that implements `prompt_logprobs`
correctly by design.

Precompiled vLLM CPU wheels (nightly and stable PyPI, both resolved to the same `0.31.0`) turned
out to be broken on this exact CPU class — confirmed via a real upstream GitHub issue
(`vllm-project/vllm#13593`) and verified via `gh pr view` that its fix (`PR #54478`) is still
open/unmerged: x86 CPU wheels ship an AMX-targeted `_C` extension plus AVX512/AVX2 fallbacks, but
the fallback files are missing from the wheel, and our CPU has AVX-512 without AMX (that's a
Sapphire-Rapids-and-later feature). Verified this by inspecting the installed package directory
directly rather than guessing. Asked the user to choose between a quick pinned-version gamble,
building from source (~20-40 min estimated), or pausing — they chose building from source.

Built vLLM from source for this exact CPU, entirely outside the project repo (`~/vllm-server/`,
isolated venv — infrastructure to test against, not a project dependency). Two further gaps
worked around without root access (no sudo on this machine):
- GCC 12.3+ required, Debian 12 only ships 12.2.0 with no backports configured — got GCC 13.4.0
  via a self-contained conda-forge environment (`micromamba`, no root, no system changes).
- `libnuma-dev` headers missing (only the runtime lib was installed) — downloaded the `.deb` with
  `apt-get download` (works without root) and extracted it locally with `dpkg-deb -x`, fixing one
  broken symlink to point at the real system runtime lib.

Build completed in 11m 34s (parameters tracked live throughout: ninja's progress counter, elapsed
time, and compiler CPU/RAM via `ps`, per the user's request to model the runtime rather than poll
blindly) and correctly produced all three ISA variants this time (`_C`, `_C_AVX2`, `_C_AVX512`).
One more real bug surfaced at server startup -- vLLM's default memory reservation (the
`--gpu-memory-utilization` flag, confusingly also controls CPU memory on the CPU backend) wanted
~29GB when only ~24.6GB was free; fixed by capping it to 0.3 (~9.4GB), which is what the user's
hardware-exhaustion concern was really asking us to watch for.

Server is now live: vLLM serving `Qwen/Qwen2.5-1.5B-Instruct` at `http://127.0.0.1:8000`
(localhost-only, never exposed). Verified `prompt_logprobs` directly via curl (exact format our
pipeline expects), then ran `scripts/smoke_test.py` for real against it:
**PASSED** -- full token alignment on all three versions, and scores moved exactly as expected
(correct -0.175 > meaning-error -0.930 > untranslated -1.349). System memory settled at 15GB free
of 31GB with the server idling, no swap used.

Documented the full working recipe in the new `BACKEND_SETUP.md` so this doesn't need
re-discovering. Both study arms are now fully unblocked.

**19:30–21:30**: a few follow-up checks on the running server to confirm it had stayed up and
the earlier verification held (no crash, no memory creep, nothing left half-finished) — server
still live at `http://127.0.0.1:8000`, resource usage still steady, nothing further to fix.
