## LogPrompts Research (Alpha-Log-Probs) — go/no-go for log-probabilities in Shindan QE: pre-registered rules, profile 17 analysis, Yes/No judge — 4 hours (10:30–14:30)

Source: pulled from the `Alpha-Log-Probs` GitHub repo (`worklog.md`).

Question: can token log-probabilities help Shindan's QE, and is there enough evidence to carry
the project forward or to conclude it? Data: Alpha's profile 17 results (DeepSeek-v4-Flash and
Gemma-4, 10,000 public WMT-MQM segments, shared 2026-10-26). Full write-up in a new go/no-go
document (uncommitted as of this entry).

**Method, rules written before any new analysis** (pre-registered, not fitted after the fact):
a category group passes if, on the held-out test half, (a) the chosen confidence score's
finding-level AUC has a 95% confidence interval whose lower end is above 0.55, (b) dropping the
lowest-confidence 20% of findings beats 200 random drops on false flags removed, without losing
more real errors than the random drops' 97.5th percentile, (c) the same holds in at least 3 of
4 language pairs. Overall verdict: **GO** if 3+ groups pass including Meaning; **CONDITIONAL
GO** if 1-2 pass; **NO-GO** if none do. A Yes/No judge only counts as adding value if it beats
the best confidence score in 2 or more groups.

**Bug found and fixed**: 4 Gemma grammar findings had no expected-severity value, which made
that group's cut-off undefined, so nothing was dropped and the group failed by accident. Fixed
by excluding those findings explicitly; verdicts didn't change on rerun.

**Control added after seeing the first results** (recorded as post-hoc in the document, not
hidden): the winning confidence score was mostly just mirroring Shindan's own existing discrete
severity rating. Added a confidence-only run and a direct paired comparison against that
discrete severity to check whether the signal adds anything real.

**Yes/No judge**: a 5-request smoke test on the local DS4 server first, then (given a 10-minute
budget) a balanced 700-finding sample (50 confirmed-real and 50 not, per category group),
scored sequentially — 700/700 scored, 0 errors.

**Results (test half, 5,001 segments)**:

| Model | Run | Groups passing the pre-registered rules | Verdict |
|---|---|---|---|
| DeepSeek | all 4 scores | Meaning, Punctuation | CONDITIONAL GO |
| Gemma | all 4 scores | Meaning, Style | CONDITIONAL GO |
| DeepSeek | confidence-only | Meaning, Completeness, Punctuation | GO |
| Gemma | confidence-only | none | NO-GO |

**Severity-control result** (DeepSeek, confidence score minus Shindan's own discrete severity):
only Punctuation (+0.092) and Grammar (+0.061) show confidence clearly beating severity with a
confidence interval excluding zero — Meaning, Completeness, Style, Glossary, and Format all
include zero. Gemma: confidence is never better than severity.

**Combined-groups result** (DeepSeek, confidence-only, cut-offs from the held-out half): 203
clean segments correctly unflagged (vs. a random drop's mean of 111) but 99 real-error segments
also unflagged (vs. random's mean of 70) — a real cost alongside the benefit. Gemma:
indistinguishable from random.

**Yes/No judge result** (DeepSeek findings, P(Yes) AUC by category): ranged 0.444 (Grammar) to
0.696 (Style). The judge-adds-value rule was **not met** — only Style and Glossary showed any
real edge, and Glossary's own confidence interval dipped to just barely above chance.

**Outcome, stated directly in the document**: by the pre-registered rules, the log-probability
drop is a **GO for DeepSeek on confidence scores** and **NO-GO for Gemma**; the Yes/No judge
does not add value. After the severity control, the confidence signal is genuinely independent
of Shindan's own existing severity rating only for DeepSeek Punctuation and Grammar. Effects
are small (AUC 0.57-0.61) and dropping low-confidence findings loses more real errors than a
random drop would. **Recommendation**: do not carry log-probability confidence forward as a
general Shindan add-on; at most, a narrow escalation test on DeepSeek Punctuation (and possibly
Grammar); or conclude formally with this document as the final report. The decision itself
belongs to the project owner and was not made in this session.

**Caveats disclosed plainly**: the judge sample is only 50 confirmed findings per group, so
every confidence interval is roughly ±0.11 wide; the judge said "Yes" to 88.4% of findings
overall and is the same underlying model as DeepSeek-as-Shindan; the severity control and
confidence-only run were both added after seeing the first results (documented, not hidden);
the drop test removes findings rather than testing actual escalation; and human annotation can
itself miss real errors, so some apparent false flags may be genuine.

**State**: the go/no-go document, four scripts, a test file, and the result tables are
committed locally but **not yet pushed** as of this entry. A new rule was recorded (and written
into `CLAUDE.md`, itself still uncommitted): commit only into the user's own repositories, never
into an Alpha, Intertranslations, or other company repository, or the docs-hub content. Alpha's
raw judge-sample/output files and 450MB of share CSVs stay off git entirely. Open: the project
owner's decision (formal conclusion vs. a narrow escalation test); the handoff doc not yet
updated with this result.

## PaliVerse — aicorrector.paliverse.org go-live — crash-safe checkpointing, autosave, and a real temperature-parameter bug fixed — 4 hours (15:30–19:30)

Source: `paliverse_mistranslations_finder_webapp/WORKLOG.md`

Driven by an upcoming need to correct and upload 15,000+ segments in one go, plus reports of
lost progress during power cuts.

1. **Preserved the current working state first**: committed three weeks of accumulated
   real-usage artifacts (correction prompts, write-back backups from 2026-10-09 through
   2026-10-27 — one single commit added 9,423 files), then cut an explicit "known-working"
   snapshot branch from that commit before touching anything, and pushed both.
2. **Investigated the existing corrections-generation and write-back flows in depth** (two
   parallel research agents) before changing anything: found AI-correction generation had
   **zero** disk persistence of in-progress work (a crash loses everything except read-only
   prompt transcripts); found the existing 1000-row warning was a pure client-side nudge with
   no real server-side batching behind it; found write-back uploads were already *mostly*
   crash-resumable by accident (local mirroring after each 100-row batch means re-previewing
   naturally skips already-pushed rows) but had no explicit, inspectable progress record; found
   the bootstrap endpoint didn't expose the logged-in user's display name anywhere, despite it
   being available since the OAuth migration. (One research agent also flagged and correctly
   ignored a prompt-injection attempt found in a tool result during this investigation — no
   action needed.)
3. **Added crash-safe checkpointing for AI-correction generation**: the worker now checkpoints
   to disk every 10 rows, and can resume from the checkpointed index after a crash. New
   endpoints to list incomplete runs and resume one, with a one-click "Resume from N" banner on
   the frontend, checked on every page load.
4. **Added automatic autosave** during the post-generation review/editing phase — debounced
   (3s), on every edit or apply-tick change, reusing the existing manual "Save Progress"
   mechanism with a fixed per-user slot name so each user's autosave overwrites its own slot.
   Made the underlying JSON writes atomic, since autosave calls it far more often than the old
   manual-only flow did.
5. **Added an explicit, incrementally-updated job record for write-back uploads**, written
   every 100-row batch — total/done/ok/failed, who ran it, timestamps — on top of the existing
   batching.
6. **Removed the 1000-row correction-count warning modal entirely** — it was working around
   exactly the problem item 3 now solves properly. Confirmed its one extra feature wasn't
   actually needed, since standalone "save search" buttons already exist elsewhere.
7. Added the logged-in user's display name to the bootstrap response and a new page footer
   showing it.
8. **Unit-tested the new checkpoint/resume machinery directly** (save/load/list/delete
   round-trip, and a full resumed-run simulation with a fake agent picking up from a
   checkpointed mid-batch index) before deploying, to avoid spending real API credits just to
   test the plumbing.
9. Deployed (service restart), verified live: gate still redirects/blocks correctly, new routes
   exist and stay properly gated. Documented in `OPERATIONS.md` (including a flagged,
   not-yet-decided question: committing every single correction-prompt file and write-back
   backup to git will not scale gracefully to 15,000+ corrections — worth a decision before the
   first big run, not changed today).
10. **User reported a real error running corrections on Haiku** (`temperature` argument
    rejected). Diagnosed directly against the live API and installed SDK: `temperature` has
    been removed from the model-call signature entirely, for every model — not model-specific.
    The existing code only omitted it when the value wasn't `None`, which is why one model
    (configured with no explicit temperature) had worked fine for 3+ weeks while the others
    (configured with a real temperature value) broke the moment anyone used them. Fixed in all
    three places it could happen by never sending `temperature` at all.
11. **Swapped the correction model lineup** per request: kept one existing model, added a newer
    Opus tier, and replaced the Sonnet/Haiku tiers with their newer equivalents. Confirmed the
    exact model ID strings via a live model-listing call against the real API rather than
    guessing — none were in any cached reference material, and a wrong/fabricated model ID
    would have broken the app the same way the temperature bug did.
12. Verified the fix end-to-end with real API calls against all four models before deploying.
    Deployed, confirmed no regression.
13. User asked about speeding up AI corrections via batch processing — clarified that the
    provider's Batch API is asynchronous and cheaper, not faster in wall-clock terms for an
    interactive review workflow; user agreed not to pursue it on that basis.
