## mini_rag (new project) — Azure-hosted RAG migration: a real leaked-credentials finding, Azure provisioning, a real regional capacity issue worked around — 4 hours (17:30–21:30)

Source: `mini_rag/WORKLOG.MD` (new entry in an existing repo)

**Context**: asked to set up a new Azure-hosted RAG for PaliVerse, multi-purpose (info-tab
explanations + a HyDE-style question-answering RAG), using the org's nonprofit Azure credits,
with chapter 1's latest info-tab generation (the Agent Unit Explanations project) as the new
benchmark.

**Two real findings from reading this repo before touching anything:**
1. **A config file has live credentials committed** — a database password, an OpenAI key, two
   Anthropic keys, a DeepSeek key, plus commented-out keys for two other providers — all in
   plaintext, in git history, right now. Flagged to the user as needing rotation and a move to
   environment variables/a secrets store, independent of anything else. **Not yet fixed** —
   waiting on the user to rotate the keys first (rotation is their call, not something to do
   unilaterally).
2. **The real pipeline is 4 API calls, not 2** — 3 Claude calls (structured expansion + HyDE
   generation, answer generation, feedback validation) plus 1 batched OpenAI embedding call,
   confirmed directly in the code, not just the README. The user had described it as a "2 API
   call" design — flagged the mismatch, not yet resolved (doesn't block today's Azure work,
   which is only about where Postgres runs).

**Azure scope decided**: lift-and-shift — keep the exact same architecture (pgvector + OpenAI
embeddings + Anthropic generation), just host Postgres on Azure Database for PostgreSQL
Flexible Server. Chosen as the cheapest, most proven option to start, matching the
nonprofit-credit budget constraint.

**Verified before provisioning**: pgvector 0.8.0+ is generally available on Flexible Server
(confirmed via Microsoft's own docs, not assumed) — the architecture is viable on Azure as-is.

**Provisioning hit a real, documented Azure platform issue.** The planned cheapest tier failed
with a SKU-unavailable error in the org's existing Azure region, even though Azure's own
capabilities API listed it as fully supported with no restriction flag. Root cause, found via
search: that region has a known regional capacity allocation constraint specifically for
Burstable-tier Postgres Flexible Server, requiring an explicit Azure support ticket to get
capacity granted — not something fixable by retrying or by CLI. Confirmed the region itself
isn't blocked in general (plenty of compute quota available) and that other regions are
outright restricted for this subscription, so the original region is the only viable one
without asking for broader access too.

**Worked around it with a different server family.** A GeneralPurpose 2-vCore tier in the same
region provisioned cleanly — real cost **$0.187/hr (~$136/month if left running 24/7)**,
markedly more than the Burstable tier's ~$14.50-29/month would have been. Verified live via
Azure's own retail pricing API, not estimated.

**What's actually live right now**: a new resource group and Postgres Flexible Server (16,
32GB Premium storage) in the chosen region; pgvector 0.8.7 installed and confirmed working;
firewall scoped to this machine's public IP only (not open to all IPs); connection details
saved to a gitignored local file, not committed, learning directly from finding #1 above.
**Server is currently stopped** (compute billing paused, small storage cost continues) —
stopped proactively right after verifying it works, rather than leaving a ~$136/month-rate
server idle overnight, given the explicit instruction to work within budget. Azure auto-restarts
a stopped Flexible Server after 7 days if not manually restarted.

**Not yet done**: migrating the existing schema and its ~2,660 chunks to this server; deciding
whether to file the Azure support ticket for the cheaper Burstable tier (adds an unknown wait)
versus accepting the GeneralPurpose cost (available now); rotating the leaked keys; resolving
the 2-vs-4-API-call question; ingesting the new chapter-1 explanation generation as a benchmark
source.
