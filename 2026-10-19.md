## LogPrompts Research (Alpha-Log-Probs) — starting the next phase: error-category spread, and moving to new hardware — started 14:00, duration not specified

Source: `Alpha-Log-Probs/worklog.md`. The source log gives only a start time (14:00) for this
block, no end time — bounded to at most 3 hours since Tikka's next session resumes at 17:00.

Next phase kickoff: evaluate how the judge technique's effectiveness spreads across MQM **error
category** (not just severity) — i.e. is it equally good at catching Accuracy errors, Fluency
errors, Terminology errors, etc., or does it specialise. Checked first, rather than assuming:
the dataset used throughout this project carries only an aggregate `score`, no error-category
field. A richer public source exists and was verified live: a Google-hosted WMT MQM repo whose
raw per-rater, per-error annotation file is the layer this project's existing data was
aggregated from — same systems, same segments, same year — carrying real `category`/`severity`
fields (27,328 rows, categories including Accuracy/Mistranslation, Style/Awkward,
Fluency/Grammar, Fluency/Punctuation, Terminology/Inappropriate for context, and others).

Also: moving this experiment to a new PC with better hardware, set up by the user directly (not
through this session — no credentials were shared with or handled by this tool, consistent with
this project's security practice throughout). The new machine will run much larger local LLMs
than the current small model and gives easier native access to logprobs — directly relevant to
the open "does this scale down/up with model size" question flagged in the Part 2 presentation
guide's scalability section.

Plan approved and implemented the same session: built a script to pull the verified error-
category annotations and a second to join them with the existing judge results via a text-based
join plus coarse category grouping. Two real problems found and fixed while building the join,
not glossed over: (1) the raw file contains literal quote characters in free text, which made
default CSV-quoting misparse the file — fixed; (2) normalizing source text for the join created
duplicate join keys on the raw-file side when two originally-distinct strings normalized to the
same text, which silently turned the join into a cartesian product — caught by an explicit
row-count assertion, not by eyeballing the output — fixed by aggregating on normalized text from
the start, with the assertion kept in the script as a permanent guard. Final join match rate
94.8% (18,698/19,725), root-caused to dataset-version text differences between the two releases,
disclosed rather than chased further. Added 5 new tests, including one that specifically
reproduces the duplicate-key bug to guard against a regression.

Built an evaluation script: category-vs-clean AUC, reusing the existing 300 already-scored
judge-pilot segments (round 1 + round 2, `gpt-4.1`/`gpt-4o-mini`) — no new API calls needed for
this first pass. Real result: **the judge specializes** — strongest on Accuracy errors (AUC
0.778-0.798), clearly weaker but still well above vLLM on Fluency (0.694-0.700) and Style
(0.711-0.743), and Terminology flagged rather than trusted (n=10 "bad" examples only, too
small). vLLM's `mean_logprob` stays at or below chance on every category (0.39-0.55), consistent
with every other result in this project. Wrote up the full result in a new results document.
29/29 `pytest tests/` pass (24 existing + 5 new). Committed and pushed.
