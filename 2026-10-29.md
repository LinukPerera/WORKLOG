### Docs-hub work-log system: what gets published, and what's still missing

Continued analysing the employer's new knowledge-base/work-log tooling (introduced 2026-10-28),
focused this time on what the lead and team would actually see — all steps stayed local; nothing
was contacted on the hub itself.

- **What it is**: the team's MkDocs knowledge base. The worklog skill keeps one page per person,
  built from git commits plus coding-agent session history; a second skill is the client that
  reads and writes pages. The page is read by the lead and the team.
- **Full sync flow**: pull the page, collect local activity, an agent writes the entries, then
  push (which refuses if the page changed on the server or shrank by more than 10%).
- **Daily automation exists but is not installed**: a scheduled task would run a coding agent
  unattended at a fixed time, limited to read/edit/write on a local copy only, no shell access.

**Local dry run of the 30-day collector** (scratch folder, no hub call): only 4 of 30 days had
anything — the earlier phase of this study (the period before the move to this PC) isn't visible
to the collector at all, since agent session history is per-machine. More significantly: **no
commits appeared at all**, even for yesterday's real commits — traced to the collector filtering
commits by git `user.email`, which isn't set on this machine, and to this repo's own commits
using two different author addresses, so even setting one email would still miss some.

**Points flagged before any real sync happens**:
- The collector reads the full text of prompts and long replies from each agent session, and an
  agent turns that into page entries — meaning pasted material and anything said in a session
  can reach a page the lead and team read. Entries need reviewing before any push; the skill's
  own rule is to leave credentials and exploit detail out.
- The collector's own timestamps for a session can differ from the times actually logged by the
  user (spot-checked against yesterday's entry) — this worklog uses the times the user gives,
  not the collector's inferred ones.
- Several environment variables still need setting before any real sync (project root, username,
  git email) — same gaps flagged yesterday, not yet resolved.
- **The hub's own API key can edit and delete any page.** Confirmed it is not in this repo and
  is not recorded in this log.

### Independently verified Alpha's Shindan "profile 17" results

Alpha shared real results on a network drive: profile 17 (DeepSeek-v4-Flash and Gemma-4) run
against 10,000 real WMT-MQM segments across 4 language pairs — a report plus four large result
CSVs. Read the report and the CSV structure, then wrote a verification script (session-scratch
only, not committed) that recomputes the headline confusion-matrix numbers directly from the
raw results.

**First run didn't match the report**: close but off (e.g. DeepSeek true-positives 5,568 vs. the
report's 5,588). Found the cause: the report's "flagged" rule also counts a separate category of
mechanical-check rows that the first verification pass had excluded. Fixed the rule to match,
re-ran — **matched the report exactly for both models.**

**Verified results** (10,000 segments, 5,885 with a real human-confirmed error):

| Model | TP | FP | FN | TN | Miss Rate | Auto-pass | Clean Auto-pass |
|---|---|---|---|---|---|---|---|
| DeepSeek-v4-Flash | 5,588 | 3,235 | 297 | 880 | 5.0% | 8.8% | 21.4% |
| Gemma-4 | 5,099 | 2,444 | 786 | 1,671 | 13.4% | 16.7% | 40.6% |

**Outcome**: the independently recomputed numbers agree with the report. The log-probability
confidence-based drop test (not recomputed directly, taken from the report) helps DeepSeek only
modestly — removes more false flags than a random drop would, but also loses more real errors
on all segments — and does not help Gemma at all (no better than random). The correct-detection
share rises with confidence for DeepSeek in meaning, completeness, grammar, punctuation, and
style, and is flat for glossary and format. Only a small minority of Shindan's own category
flags actually match the human raters' category.

**Caveat, stated plainly**: only the segment-level confusion-matrix counts were independently
verified; the drop-test tables, confidence-band breakdowns, and category figures are taken from
the report as given, not recomputed here. The report's own disclosed caveats: one run per model,
a draft category mapping, the 20%-cutoff and random-control choice made after seeing the en-de
results, a few hundred segments per pair overlapping an earlier benchmark, one language pair's
glossary step running without an actual glossary, and finding text not read during scoring.

**Not yet tested**: escalation to a second model — the actual core of the proposal. Only the
simpler "drop low-confidence findings" approach has been tested so far.
