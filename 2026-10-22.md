### Mechanical edit classification & statistics

Ask: stats on which sentences were edited multiple times, plus mechanical classification of
every edit (char/word counts, punctuation-only vs. real changes, etc.) — as many mechanical
categories as could be derived.

Pulled all 68,174 currently-published change rows (grown from 67,067 the day before — live
production data, edits keep happening). For every change, computed char/word deltas, a
Levenshtein-distance proxy (via `difflib` opcodes), and a mutually-exclusive primary category in
priority order: formatting-only, whitespace-only, case-only, punctuation-only, numeric-only,
diacritic-only, then substantive (split into minor/major by edit size). Aggregated per segment
across its whole edit chain: edit count, net char/word delta original→final, per-category
counts, distinct editors/publishers, and a "reverted to an earlier state" flag.

**Headline numbers**:
- 43,678 distinct segments have ≥1 published edit; 11,631 edited 2+ times; 1,576 edited 5+
  times; 1,079 edited 6+ times.
- 2,073 touched segments ended up with final text identical to their original (all the churn
  was formatting/punctuation/reverts — net zero text change).
- 4,768 segments show a revert-to-earlier-state pattern.
- Category split across all 68,174 changes: 92.29% substantive, 6.56% punctuation-only, 0.97%
  formatting-only, remainder (case/whitespace/numeric) each under 0.1%. Zero pure
  diacritic-only edits found.
- Bulk find-and-replace actions dominate (60,000 of 68,174 changes), followed by individual
  frontend edits (3,937), restores (2,233), imports (1,151), single edits (853).
- Per-editor: the two most active accounts made 36,089 and 27,904 edits respectively, across
  over 20,000 segments each; a third made 3,102 (including 657 formatting-only); the remaining
  three accounts made far fewer.

### MQM error-classification framework: design, pilots, and full run

Ask: design a taxonomy of translation-error types (grammar, meaning, mistranslation,
offensiveness, etc.) to find the biggest problems in the translation pipeline — cheap and quick,
but accuracy first.

Built a 7-category/19-subcategory MQM-style taxonomy. Quantified real scope first: of 68,174
published changes, only "substantive" ones are candidates. Corrected the unit of analysis after
the first pilot and the user's feedback: classification compares each segment's **original**
text against its **final** text, not every intermediate edit step — also caught and fixed a bug
where a segment whose only net change was punctuation was still being sent to the classifier.
Corrected scope: **38,836 segments** genuinely need classification.

**Local model pilots (a small local LLM) — three designs, three failures**, per the user's
request to try the cheapest option first: single-label (69% of sampled segments collapsed onto
one category regardless of content), multi-label JSON (same collapse, plus parse failures), and
a 7-way yes/no-per-category design using the model's own token probabilities as a
confidence score (architecturally sound, but the model said "yes" to 5-6 of 7 categories per
segment regardless of content — bias, not discrimination). Extrapolated full-run time: 316-486
hours depending on design. Per the user's own pre-agreed fallback, this cleared the bar for
switching models.

**Decision point**: while investigating where to source an API key, found the existing
production PaliVerse mistranslation-finder app already has a configured Anthropic key. Flagged
this to the user before proceeding rather than silently reusing or touching that app. User's
direction: keep this analysis separate from that app, but reuse its already-configured
(read-only use) API key for the classification work here.

**Claude Haiku pilots**: switched to structured JSON output with an enum-constrained schema, so
an invalid label is structurally impossible. A 40-item batch showed one category dominating —
inspection confirmed this was genuine (a real, consistent recurring correction), but exposed a
real ambiguity the model couldn't resolve from text alone: is a recurring correction an isolated
fix or a deliberate bulk consistency pass? **Fix**: added a "how this segment was edited" context
field (bulk find-and-replace vs. individual edit vs. a mix) with one prompt sentence telling the
model which label family to prefer accordingly — the single biggest quality fix in the whole
pipeline. Re-ran the same batch: label distribution became sensible and varied. A 200-item
validation batch (user-requested, to check quality held up before the real spend) came back with
0 invalid labels and 0 parse failures across both rounds; manually spot-checked several
multi-label cases and judged the results good enough to proceed (actual cost ≈$0.44).

**Repo setup**: before pushing anywhere, found and fixed a real security issue — 5 scripts had
the database password hardcoded in plaintext. Extracted credentials into a gitignored `.env`
(with an example file committed instead) and a shared config helper; verified no secret strings
remained in the staged diff before committing. Created a new private repo
(`paliverse-segment-edit-analysis`) and pushed the initial commit — scripts, the SQL report, the
taxonomy, and the write-ups so far. Large generated data dumps were gitignored, not committed
(regeneratable from the scripts).

**Full run submitted and collected**: the user approved the full run (≈$37 via the Batches API's
50% discount) after the 200-item validation. Submitted 8 batches, 38,836 segments total. All 8
batches completed within a few hours — **0 errored requests, 0 JSON parse failures across all
38,836 segments**, the structured-output constraint holding at full scale. Actual cost:
**$35.55**, in line with the pre-run estimate.

Headline result from the full run: terminology-consistency work dwarfs outright meaning errors
(~42% of flagged issues are terminology standardization/inconsistency vs. ~7% genuine accuracy
problems). Two label categories (sensitivity issues, and non-error import/revert tags) never
fired once across all 38,836 segments — plausibly genuine, not confirmed absent, since reverts
are already tracked separately by a different signal in the mechanical-classification step.

## PaliVerse Segment Edit History Investigation — deep-dive analysis of the full classification results — 3.5 hours (16:00–19:30)

Source: `segment-history-db/WORKLOG.md`

Deep-dive work on the morning's full-run classification results, producing four reports:

1. **Cross-cuts by editor, book/file, category co-occurrence, and time**, with a 0-5 severity
   weight to rank "biggest problem" by impact rather than raw count. Key leads: one book stood
   out as a priority QA target (612 segments, 44.9% accuracy-issue rate — not a small-sample
   fluke); genuine mistranslation fixes almost always co-occur with sentence restructuring, not
   isolated word swaps; the accuracy-issue rate swings hard by month (5.2% in a bulk-work month
   vs. 53.6% in another) in a way that tracks what kind of work was happening, not a clean
   quality trend over time.

2. **Content-level pattern analysis** — per the user's ask to look at the actual *content* of
   the problems, not just meta-statistics: parsed every flagged issue's before→after evidence
   text and grouped recurring patterns. Found a genuine, scoped, fixable pipeline bug: a bulk
   epithet replacement breaks on embedded grammar in commentary files, producing malformed
   hybrid words — confirmed in 297+ segments, concentrated almost entirely in two file types,
   directly explaining why those files topped the severity ranking above. Also found: two
   formulaic canonical phrases mistranslated the same wrong way hundreds of times each (fixable
   at the template level, not segment-by-segment); a systematic gender-neutrality correction
   pattern (156+ occurrences, one direction only); and nine terminology decisions that together
   account for ~26% of all flagged issues and should move into the base glossary rather than
   being re-fixed book by book.

3. **Focused look at the highest-volume editor's own edits**, per the user's request: this
   account is 91.5% bulk find-and-replace (median edit size 8 characters), with activity
   tripling month over month, and its top recurring correction patterns match the corpus-wide
   terminology decisions from the previous finding almost exactly — strong evidence this account
   is the one executing that standardization sweep. Its own accuracy-issue rate (~18%) is still
   well above the corpus average (~7.3%) though, so it's not purely mechanical.

4. **Isolated one-off edits from bulk work**, per the user's request — the most significant
   single finding of the day: one-off edits are a *structurally different population*, not just
   a smaller sample of the same thing — ~10x higher genuine-mistranslation rate (29.6% vs. 3.1%
   for bulk-touched segments), bigger edits, and the large majority of their recurring patterns
   occur exactly once (real one-of-a-kind judgment calls). Also surfaced a terminology choice
   resolved two different ways between one-off and bulk edits, and the same book confirmed as a
   hot spot from a second, independent angle.

All four reports committed and pushed to the project repo. No further API spend was needed for
any of this deep-dive work — all four analyses read from already-collected results.
