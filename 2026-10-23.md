## Tikka translation process — Info Tabs: adopted the client's developer brief/prompt, dry run then live run across 3 providers — 5 hours (13:30–15:30 and 16:30–19:30, split by the LogPrompts Research meeting below)

Source: `Tikka_translation_process/WORKLOG.MD`

**Client sent a real developer brief + prompt** (Michael Xynos, v1.0, dated 2026-10-21).
Fetched and read it directly. Scope: adopt the client's prompt for DeepSeek, Claude, and Meta
only (not Gemini) — working around the client's sequential/no-cache technical design since this
project already has a working chapter-wide caching architecture. Starting with S0101 Chapter 1
again, dry run first.

**What the brief specifies**, so every adaptation below is traceable back to it: a
phrase-by-phrase walk through the segment (bold heading = verbatim quote from the root text, in
order), "the commentary says/explains/adds" for commentary content, "the sub-commentary
adds/notes/records" only when it changes the meaning, a "For the reader:" line only on phrases
that carry a teaching, closing with a question to sit with — no title, introduction, summary,
glossary, or synthesis (a genuinely more minimal format than this project's own earlier
reconstructed prompt). First line of every output is a merge decision (how many segments, up to
3, the model chose to cover together). Sub-commentary is Pāli-only for now — the model must read
it in Pāli but never quote Pāli in the English output. Strict no-scholarship,
no-forward-reference, no-Pāli-outside-headings rules, with concrete automatic acceptance checks
(word-count bands, verbatim-heading check, forbidden-phrase check) the brief itself specifies.

**Built the adapted prompt and ran the dry run** (zero API cost, S0101 Chapter 1, 149 segments).
The real divergence from the client's design is architectural, not content: their design resends
this-segment-only commentary fresh every call (no caching); this pipeline keeps the existing
chapter-wide caching (confirmed 8.9x cheaper at this scale on 2026-10-19/20) and instead adds an
explicit instruction telling the model exactly which commentary unit(s) it may draw on for a
given call, with the rest of the cached block to be treated as not given — the same "do not go
beyond the supplied texts" rule the brief already states, just enforced by instruction instead
of by never sending the rest. New capability built: lookahead for the client's merge-decision
mechanism, which this project's existing pipelines never needed before (they only ever looked
backward).

**One field intentionally not optimised away, because it's a content requirement, not a caching
one**: a "prior explanations" field genuinely needs the real prior output of a true sequential
run (merge decisions shift the segment pointer, exactly as the client's own processing-loop
pseudocode describes) — a dry run can't fabricate that, so it's an honest placeholder for now.
The live run needed real sequential processing per sutta (not parallel) for this reason — kept
from the client's design deliberately, since avoiding it would mean the model couldn't actually
avoid repeating itself across segments.

**Caught and fixed a real bug before trusting the dry run output**: sub-commentary showed "NOT
SUPPLIED" for all 149 segments on the first pass — the script only looked at each root unit's
own bold row for the sub-commentary link, missing the two-hop fallback (via the linked
commentary unit's bold row) that every other pipeline in this project already uses. Fixed by
reusing that same fallback. Corrected result: **137/149 segments have real Pāli sub-commentary,
12/149 genuinely lack it** — spot-checked real Pāli text directly, not just trusted the
non-empty field.

Dry run output written to disk (149 files). Not yet wired to any live provider call — structure/
correctness review only, same discipline as every other dry run in this project.

**Built and validated the real sequential live runner** for DeepSeek, Claude, and Meta
Contributor — genuinely sequential per provider/sutta (the brief's own requirement): each call's
prompt includes the real stored output of every segment/group already covered, and the pointer
advances by whatever the model decides to cover. Implemented the brief's automatic checks
(first-line format, verbatim headings in order, exactly one closing question — auto-regenerate
once on failure, as the brief specifies; word-count band, no stray Pāli diacritics, no
forbidden forward-reference phrases — flagged for review, never auto-rejected, matching the
brief's own review-not-reject rule).

**Real bugs found and fixed during validation, not assumed away:**
- DeepSeek's first real test came back completely empty — the same reasoning-model failure
  mode already fixed once before (hidden reasoning consumes the whole output budget before any
  visible text). Raised the output-token cap to match that earlier fix.
- Claude's SDK refused the call outright above a certain token budget ("streaming is required
  for operations that may take longer than 10 minutes") — a real, documented SDK requirement,
  not a bug on this project's side. No cost incurred (failed before sending). Fixed by switching
  to the streaming call and accumulating, instead of the plain blocking call used everywhere
  else in this project so far.
- The heading-verbatim check failed on output that was actually correct: one provider used a
  curly apostrophe where the source root text has a plain one — models routinely "prettify"
  punctuation even when told to quote verbatim. Added typography normalisation before comparing.
- Claude wrapped bolded headings in an extra pair of quotation marks — clarified the prompt
  wording, and made the check strip a matching leading/trailing quote pair as a safety net.
- Both Claude and Meta Contributor italicised the entire closing-question line instead of just
  the label — an equally valid, visually identical rendering the brief's own wording doesn't
  rule out. Loosened the check to match either form rather than fail on cosmetic markup.

**After all fixes, all 3 providers pass the hard checks cleanly on the first attempt** (real
validation calls, small real cost: Claude $0.7753 for one cold cache-write, Meta Contributor
$0.0092 for a 2-segment merge, DeepSeek $0.1424 for 1 segment). Each provider made its own real
merge decision from the system prompt's rules, not a hardcoded default.

**Ran the full chapter for all 3 providers, per the client's direction.** All completed 149/149
segments, genuinely sequential, real merge decisions throughout:

| Provider | Real calls | Real cost | Wall-clock | Cache hit ratio |
|---|---|---|---|---|
| Claude | 98 | **$74.98** | 149.8 min | 46.8% |
| DeepSeek | 94 | $8.16 | 189.8 min | 67.7% |
| Meta Contributor | 86 | **$0.75** | 100.3 min | 37.6% |

**Total real cost: $83.89 for one chapter, three providers.** Claude is ~17x Meta Contributor's
cost and ~9x DeepSeek's — the real economics of this richer, sequential, merge-aware pipeline at
Claude's price point, not a bug. Merging worked as intended across all three (149 segments
collapsed to 86-98 real calls).

**Hard-check failures concentrate almost entirely in the sutta's own structurally repetitive
sections, not randomly** — a long catalogue-of-views section the client's own test plan already
flagged by name, and a deliberately repetitive recollection-of-past-lives formula the model
legitimately abbreviates. One failure (DeepSeek, a divination-list segment) was spot-checked and
found to likely be a limitation of the automated order-check on long, repetitive, comma-heavy
enumerations, not a confirmed defect in the real output — flagged honestly as unverified rather
than claimed either way.

**What's still needed, per the brief's own next-steps section**: the check that matters
most — whether every commentary/sub-commentary attribution is actually supported by the
supplied text — needs a human reviewer who reads Pāli (the sub-commentary is Pāli-only per the
brief's current state), so it isn't automatable here. Recommended next step: send flagged
segments (and a clean sample) to Ven. Ñāṇadassana for review, adjust the prompt from findings,
re-run the chapter, then proceed — not a one-shot process.
