## PaliVerse RAG — full-canon ingestion run completed, then a real retrieval architecture bug found and fixed — 4 hours (10:30–14:30)

Source: `mini_rag/WORKLOG.MD`, referred to here as "PaliVerse RAG"

**Started the real, full ingestion run** — all 738 (file, chapter) pairs across the 59 root
texts, no limit, embedding included. Launched detached so it survives independent of any single
tool call, logging to a scratch file, confirmed running independently right after launch. The
real OpenAI key was swapped into the config only long enough for the process to load it into
memory at startup, then reverted on disk immediately after — the long-running process keeps its
own in-memory copy, so the committed file stays on the dead key throughout the run.

**Chunk-build phase: actually much faster than estimated, and much bigger than projected.** All
738/738 chapters completed in well under an hour. Real totals: **61,112 canonical + 148,551
commentary + 32,733 sub-commentary = 242,396 chunks** — about 3x the ~79,000 projected in the
previous day's sizing estimate. Reconciled why: that estimate scaled by raw row count, but
commentary texts pack far more chunks per unit than root texts do after the chunking budget —
the estimate's error was in assuming uniform density across layers, not in the underlying
row-count scaling itself (which held up fine for storage/token purposes, just not for chunk
count).

**Real bug found and fixed: the embedding dedup check was the actual bottleneck, not embedding
itself.** After chunk-building finished, the run went quiet for over an hour with almost no CPU
activity — a clear sign of waiting on network round-trips, not computing. Diagnosed directly on
the Azure server: it was mid-way through a per-chunk existing-embedding lookup, called once per
chunk — fine at chapter-1 scale (~3,765 chunks) but became the real bottleneck at ~242,000
chunks, one network round-trip per row. Killed the process safely (verified the chunk-build data
was already committed, and that zero embedding work had actually been lost). Fixed by replacing
the per-row lookup with one batched query, then an in-memory comparison per chunk — dedup for
all 242,396 chunks now takes seconds instead of threatening another hour-plus.

**Embedding re-launched with the fix — genuinely fast now**: 241,039/242,396 chunks embedded
cleanly in ~57 minutes.

**Second real bug found immediately after** — the run "succeeded" but the chunk-type breakdown
was wrong: the chapter-1 benchmark's synthetic chunks had vanished entirely. Root cause: the
full-canon script's per-chapter prune step ran for chapter 1 too, since it's one of the 738
pairs — and since this driver deliberately never produces synthetic chunks (no permission yet
for full-canon AI explanations), its prune logic correctly-by-its-own-logic, but
wrongly-in-effect, deleted the real chapter-1 benchmark chunks as "stale." **Recovered, not
lost**: the real benchmark files still exist on disk, so re-ran the original, narrower ingestion
script scoped to chapter 1 — restored all 2,408 synthetic chunks and their embeddings without
touching any of the other 242,396 chunks from the rest of the canon. Re-applied the
needs-review tagging for the two known-ungrounded units (lost in the same delete/recreate).
**Fixed the root cause** in the full-canon script too, so this can't recur on any future re-run.

**Final, real, verified numbers**:

| Metric | Result |
|---|---|
| Total chunks | **244,804** (61,112 canonical + 148,551 commentary + 32,733 sub-commentary + 2,408 synthetic) |
| Total embeddings | **244,804** — every chunk embedded, confirmed via a direct count match |
| Quality status | 36 needs-review (the two known units) / 244,768 verified |
| Total DB size | **~5.0GB** — close to the ~5.6GB projected the day before; that projection held up |
| Total tokens embedded | **48,003,287** — about 3x the ~16.1M projected the day before, same root cause as the chunk-count miss |
| Real embedding cost | **~$6.24** — still cheap, but a real, honest correction to the earlier estimate rather than letting the old number stand |

What this run deliberately does **not** include, per the agreed scope: glossary, knowledge
graph (still blocked on an unreachable source file), and AI-generated explanations for anything
beyond chapter 1's existing benchmark.

**Post-migration verification, within the same session.** Built a two-part verification script:
data-integrity checks (chunk/embedding counts, duplicate keys, citation resolution, per-root
coverage, embedding model/version consistency, orphaned rows), plus real end-to-end question-
answering calls against texts *other than* chapter 1, to prove the pipeline actually works
across the newly-loaded corpus, not just that chapter 1 still works.

**Data-integrity checks: 6/6 pass.**

**A real, serious architecture bug found — exactly what this test was built to catch.** All 3
non-chapter-1 queries returned only chapter-1 content, regardless of topic. Root cause: the
retrieval code has always hard-filtered its vector search to one configured root text — this
project was built as, and the retrieval code still behaved as, a single-discourse test bed.
Loading the whole canon's data never made it reachable, because retrieval itself was still
hard-scoped to one text. A second, related bug in the same function: the "pull full commentary
for the top-ranked unit" expansion step used that same single global text instead of each
candidate's own root text — since unit IDs aren't globally unique across different root texts,
this could have silently searched the wrong text entirely for non-chapter-1 content.

**Fixed both**: removed the hard text filter from the candidate-retrieval query entirely —
search now spans every chunk in the database, not one configured text. Added the candidate's own
root text to that query's output so the commentary-expansion step can use it instead of the
global config value.

**Re-tested after the fix: 3/4 pass, one real remaining finding.** Two of the three
previously-broken queries now correctly retrieve from their real sections — the architecture fix
works. The third (a Vinaya training-rule question) retrieved plausible-but-wrong content from a
different text entirely. Checked directly: real relevant content does exist in the corpus (over
15,000 chunks from the actual Vinaya texts, several explicitly on-topic) — so this is a genuine
retrieval-ranking miss for that specific query, not a content gap and not the same bug as above.
Flagged as a real but narrower finding, not fixed today — likely related to HyDE passage quality
or diversity-cap tuning at this much larger corpus scale, worth its own investigation later
rather than a quick patch.

**Not yet done**: investigating the ranking miss further; re-running the original 6-question
demo set against the fixed retrieval code, since the fix changes retrieval behavior for every
query, not just the newly-tested ones.

## PaliVerse RAG — connecting passages via pure embedding similarity, for info-tab generation — 6 hours (16:30–22:30)

Source: `mini_rag/WORKLOG.MD`

**Goal, as the user framed it**: start wiring the RAG into the info-tab generation process by
finding genuinely connected/relevant passages to each other, and keep tuning until retrieval can
pull the right content by embedding similarity alone — no extra LLM call needed at that step.

Built a measurement script to check this concretely rather than guess: reuses the same
top-5-recovery methodology already established in the Agent Unit Explanations project (known
root-to-commentary links as ground truth), but run across the whole canon using embeddings
already computed for this project — zero new API calls, since it's pure SQL/vector-search
against data already on hand. Two scopes: pulling a unit's own commentary via embeddings alone
(directly useful for info-tab generation), and genuine whole-canon cross-corpus discovery with
no root hint at all (the harder, more ambitious version of "find connected passages").

**Two real bugs found and fixed before trusting any number** — the first attempt gave a
nonsensical 2.6% recovery, nowhere near plausible:
1. Re-binding a vector fetched from one query as a parameter in a second query needs an
   explicit conversion — a type error the first attempted fix didn't anticipate either.
2. The real cause, found after the type fix still gave 2.6%: compared the known link's
   commentary-side unit numbering against a candidate's *root*-unit numbering — two different ID
   spaces, confirmed directly against the real linking code rather than assumed. Fixed to
   compare against the correct field. A related issue for the whole-canon scope specifically:
   unit IDs aren't globally unique across different commentary files, so that comparison now
   uses (file, unit) pairs instead.

**Real result, same-text scope, in progress — genuinely promising.** Running total through
10,000 of 31,588 known links tested: recovery hovering 60-80% per batch (full aggregate not in
yet) — already in the range of the established CPU-model baseline (79.73%/78.38% from the two
models benchmarked earlier), on a sample roughly 200x larger than the original chapter-1-only
benchmark. This is a real signal that the embedding model this project already uses (no GPU, no
new infrastructure) can connect a passage to its real commentary via embedding similarity alone,
often enough to be useful. Final aggregate number and the harder whole-canon scope still to
come.

**Embedding model alternatives researched while the benchmark ran**, since the provider-
recommended model from two days ago remains blocked by a zero-GPU-quota wall (confirmed
universal across every GPU family/region on this subscription, not just the usual region).
Findings: hosted multilingual embedding APIs exist elsewhere but none confirm explicit
Pali/Sanskrit support without checking further; no CPU-runnable or hosted build of the
recommended model itself was found (only quantized versions of its sibling translation/
instruction models, not the embedder); a near-zero-effort upgrade candidate exists — same CPU
setup as the current baseline, measurably better on a standard retrieval benchmark. Full write-up
to follow once the benchmark run finishes.

**Logging off for the day with the run still in progress.** Last confirmed checkpoint: 12,000 of
31,588 links tested, cumulative recovery 68.4%. Left running unattended in the background
(survives this session ending) — the final aggregate number, and the harder whole-canon scope,
to be reported in a future session once it completes.
