## PaliVerse — segment edit history investigation (new) — 0.5 hours (13:00–13:30)

Source: `segment-history-db/WORKLOG.md` (new project folder, created fresh for this task).

The user reported that some translation segments on the PaliVerse production site have been
edited 5–6+ times, and asked whether the **original** text could be compared against the
**final (current)** text for each such segment, along with the **user(s) who made the
changes**. Investigation was performed directly against the production database using a
scoped, read-only account supplied by the user.

**Setup**: no MySQL client was installed; created a Python virtualenv and installed `pymysql`
into it. Confirmed the target is MySQL/MariaDB protocol (not Postgres).

**Schema discovery**: two relevant tables — one row per editor action/event (6,707 rows: type,
status, created-by, published-by, timestamps, a human-readable summary, JSON detail blobs), and
one row per field-level text change linked to its parent action (67,125 rows: segment id, old
text, new text, integrity hashes, status, timestamps).

**Data-shape verification**:
- Confirmed `status` distribution (67,067 published, 36 pending-review, 22 rejected) — only
  published rows represent text that's actually live, so the original-vs-final comparison
  filters on that.
- Confirmed each segment id never spans more than one language, so it's a safe grouping key.
- Confirmed import-type actions still carry a real old/new text pair, so they're correctly
  included in the chronological chain rather than treated as a null baseline.
- Attempted to resolve the numeric editor/publisher user IDs found in the data (1, 5, 9, 14, 36,
  69, 80) to names — denied: the read-only account is scoped to exactly the two tables above and
  nothing else. **Hard limitation**: with this login, editors/publishers can only be reported as
  numeric WordPress user IDs, not names.

**Core analysis**: joined changes to actions (published only), grouped by segment, took each
segment's first old-text as "original" and last new-text as "final," counted total published
edits, and collected the distinct editor/publisher IDs involved.

**Results**:
- 42,655 segments have at least one published edit.
- **1,576 segments have been edited 5 or more times; 1,079 edited 6 or more times.**
- The most-edited segment has **21 published edits**, spanning about six weeks, touched by 3
  distinct user IDs.

Also wrote a pure-SQL equivalent of the same report (no Python needed) and verified it
reproduces the Python results exactly, row-for-row.

**Open items**: editor/publisher names (not just numeric IDs) need a login with access to the
WordPress users table, or a supplied ID→name lookup table for the 7 IDs found; pending-review
and rejected changes were deliberately excluded (flagged in case those are wanted too); restore
actions are counted as ordinary edits (deliberate, not an oversight).
