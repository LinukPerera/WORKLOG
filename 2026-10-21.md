## PaliVerse — segment edit history investigation (new) — 0.5 hours (13:00–13:30)

Source: `segment-history-db/WORKLOG.md` (new project folder, created fresh for this task).

The user reported that some translation segments on the PaliVerse production site have been
edited 5–6+ times, and asked whether the **original** text could be compared against the
**final (current)** text for each such segment, along with the **user(s) who made the
changes**. Investigation was performed directly against the production database using a
scoped, read-only account supplied by the user.

**Setup**: no MySQL client was installed; created a Python virtualenv and installed `pymysql`
into it. Confirmed the target is MySQL/MariaDB protocol (not Postgres).

**Schema discovery**: two relevant tables — one row per editor action/event (6,707 rows: type,
status, created-by, published-by, timestamps, a human-readable summary, JSON detail blobs), and
one row per field-level text change linked to its parent action (67,125 rows: segment id, old
text, new text, integrity hashes, status, timestamps).

**Data-shape verification**:
- Confirmed `status` distribution (67,067 published, 36 pending-review, 22 rejected) — only
  published rows represent text that's actually live, so the original-vs-final comparison
  filters on that.
- Confirmed each segment id never spans more than one language, so it's a safe grouping key.
- Confirmed import-type actions still carry a real old/new text pair, so they're correctly
  included in the chronological chain rather than treated as a null baseline.
- Attempted to resolve the numeric editor/publisher user IDs found in the data (1, 5, 9, 14, 36,
  69, 80) to names — denied: the read-only account is scoped to exactly the two tables above and
  nothing else. **Hard limitation**: with this login, editors/publishers can only be reported as
  numeric WordPress user IDs, not names.

**Core analysis**: joined changes to actions (published only), grouped by segment, took each
segment's first old-text as "original" and last new-text as "final," counted total published
edits, and collected the distinct editor/publisher IDs involved.

**Results**:
- 42,655 segments have at least one published edit.
- **1,576 segments have been edited 5 or more times; 1,079 edited 6 or more times.**
- The most-edited segment has **21 published edits**, spanning about six weeks, touched by 3
  distinct user IDs.

Also wrote a pure-SQL equivalent of the same report (no Python needed) and verified it
reproduces the Python results exactly, row-for-row.

**Open items**: editor/publisher names (not just numeric IDs) need a login with access to the
WordPress users table, or a supplied ID→name lookup table for the 7 IDs found; pending-review
and rejected changes were deliberately excluded (flagged in case those are wanted too); restore
actions are counted as ordinary edits (deliberate, not an oversight).

## LogPrompts Research (Alpha-Log-Probs) — detailed project proposal with Mr. Antonio (Alpha): confidence-based escalation for Shindan with log-probabilities — 5.5 hours (18:00–23:30)

Source: pulled from the `Alpha-Log-Probs` GitHub repo (`worklog.md`).

The user wrote a detailed project proposal with Mr. Antonio from Alpha, "Extending Shindan with
Log-Probabilities." The user's part was the Technical Implementation section and the project
timeline.

**Goal and starting ideas (from the meeting)**: reduce Shindan's false positives (errors it
reports that are not real, concentrated in some categories) without increasing false negatives,
by using log-probabilities as a confidence score and escalating doubtful cases to a stronger
model whose verdict is final (the "Trust or Escalate" approach). Ideas discussed: quantifying
the probability a reported error is real; category-specific log-probability checks; plain
segment-level QE benchmarked against CometQE and MetricX. Tversky-index filtering was ruled out
because it needs fine-tuning, which this plan does not do.

**Design decisions**:
1. **Main method**: confidence comes from the log-probabilities of the words in Shindan's own
   verdict, read from the call Shindan already makes (no extra model call needed), calibrated
   per category against human annotations so a score of 0.8 means about 8 in 10 are correct.
2. **Evidence and its limit**: this project's own tests on public data found the confidence of a
   Yes/No verdict reached AUC 0.749 (0.80-0.82 for mistranslation, ~0.60 for terminology, chance
   for terminology-inconsistency/spelling), while the log-probabilities of an existing
   translation only gave AUC 0.49-0.53 (not used). Shindan's own output specifically hasn't been
   tested yet.
3. Since Shindan runs one LLM per category on every segment, the category is already known (not
   derived from log-probabilities), a separate per-error-kind experiment was dropped as
   redundant, and a low-confidence "no error" verdict can also be double-checked for free,
   giving a route to catch missed errors (measured separately from false-positive reduction).
4. **Escalation rule, per category**: keep a detection when confidence agrees with Shindan and
   is above the category cut-off; below cut-off or disagreeing, escalate to a trusted
   mid-tier model first, then a stronger model whose verdict is final. Candidates for that
   model chosen by experiment (DeepSeek-v4-Flash, Gemma-4, the mid-tier model, a commercial
   model only if necessary).
5. **Recall protection**: a detection is dropped only when the double-check is clearly sure it's
   not an error; if even the stronger model is unsure, the case goes to a human post-editor
   (design choice, to be confirmed with Alpha).
6. **Cut-off selection**: per category, on held-out annotated data, the cut-off sending the
   fewest cases to escalation while the error rate among kept cases stays below an agreed limit,
   at a stated confidence level — checked against the source paper's method (fixed-sequence
   testing, exact binomial bound, failure probability split across cascade stages). Sample
   sizes computed: 29-39 zero-error kept cases certify a 10% risk; in practice ~150-300
   annotated detections per category above cut-off.
7. **Fallbacks**: if Shindan doesn't return log-probabilities, ask the same model one short
   Yes/No question per error and use that confidence; if confidence doesn't separate right from
   wrong in a category, or annotated data is too thin, that category keeps Shindan's current
   output — never worse than today.
8. **Experimental side track** (not the main plan): a Yes/No check on the exact flagged words,
   adopted for a category only if it clearly beats the main method on held-out examples.

**Evaluation design**: the standard WMT-MQM set from Alpha's own knowledge base (2,500 segments
each for en-de/en-es/en-ru/zh-en, 10,000 total; human MQM categories and severity), mapped to
Shindan's seven categories. Procedure: count annotated errors, define a correct detection, run
Shindan once with log-probabilities recorded, split by source sentence for cut-off-setting vs.
testing, compare Shindan alone / the escalation pipeline / random escalation / CometQE-or-MetricX-
chosen escalation, report precision/recall/F1 per category and language pair with confidence
intervals. Data-feasibility estimate per category (scaled from this project's own English-German
2022 counts, to be replaced by real counts) flagged one category as likely too thin to validate.

**Timeline and wording decisions**: an initial 5-6 week estimate was judged far too long (the
whole QE framework so far took under two months); compressed to **~2 weeks plus a 1-week
buffer**, based on code reuse from this project's earlier experiments and its own pace (13 days
for the full study so far). Wording deliberately avoids promising a "guarantee" — a result with
a stated confidence level, per category, where the data allows. Realism flags raised: the
trusted mid-tier model's reported accuracy on a public benchmark subset could be optimistic if
the 10k set overlaps its own training/dev data; the "no extra call" claim depends on Shindan
actually returning log-probabilities. Several open questions sent back to Alpha (whether Shindan
returns per-category log-probabilities, annotation structure of the 10k set, who runs Shindan on
it and how long that takes, etc.).

**State of the files**: the Technical Implementation rewrite is in the repo copy of the proposal
document. Suggested edits to the Evaluation/Timeline/Expected-Results sections are drafted in
two new working-draft files, not yet applied to the Word document and not yet committed.
