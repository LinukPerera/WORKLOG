## Agent Unit Explanations (new project) — repo scaffolded, entity search and prompt pipeline built across 4 revisions, full chapter build started — 8.5 hours (15:00–23:30)

Source: `agent-unit-explanations/WORKLOG.MD` (new project, replacing the Tikka-side Info Tabs
pipeline with a richer, agentic design)

**Repo created and scaffolded.** No create-repo permission existed under this GitHub account in
the org, so the user created the repo instead. Cloned, scaffolded per the user's own written
coding-agent instructions (`AGENTS.md`), with the suggested folder layout.

**Phase 1 preflight, run for real against the live DB.** 149 contiguous root units (S0101
Chapter 1), no empty root text, 148/149 commentary-linked (one real gap), glossary (24,798
rows) and lemma table (287,062 rows) both load. One real Claude Haiku test call confirmed the
key works and a cache hit confirmed prompt caching works. Two real bugs found fixing the checks
themselves: one check was a trivial self-referential pass; the real test (lemma table vs.
chapter 1's own root vocabulary) found 0/1,743 overlap at first, traced to a staging script
building that table from the wrong text type — retested against the correct source, 37% real
coverage, not a gap.

**Phase 2 decisions:** download two embedding models for a benchmark (approved); a $150 budget
ceiling set; investigated three named figures by hand to resolve ambiguous mentions — two are
real root-text mentions, one has a real but non-narrative aside, and one is genuinely absent
from chapter 1 (zero hits across root + commentary + sub-commentary), confirmed with hard
evidence (the chapter's own closing formula appears right where expected) — a real sutta
boundary, not a linking gap. Built a new output table rather than reusing an existing empty one,
and a doc listing every table/file touched.

**Embedding benchmark: multilingual-e5-large wins** (79.7% vs. BGE-M3's 78.4% top-5
hierarchy-link recovery, English root as query). Pali embedded directly scores far worse for
both models, confirming commentary English is the right thing to search, not raw Pali
similarity.

**Mechanical entity search, built then stress-tested against real data — this is where most of
today's real bugs were, and fixing them is most of what made later stages trustworthy:**
- Naive substring search for one name matched inside an unrelated, longer compound name
  elsewhere in the book. Fixed to whole-word matching.
- Diacritic-folding two names that are phonemically distinct in Pali (vowel length is phonemic,
  not a spelling variant) as if they were the same word. Fixed by recording the literal spelling
  matched on every hit, so a mixed-spelling result flags itself.
- The automatic candidate-discovery step first scanned the whole 13-chapter book, surfacing
  other chapters' title characters as if they were chapter-1 candidates. Fixed to scope by
  chapter and the real hierarchy link.
- Searching only chapter 1's own three files reported one well-documented figure as essentially
  absent — the user correctly called this out as a fatal-looking gap. Real fix: the DB holds the
  whole corpus (174 source files), not just this book — that figure's framing is real and
  citable elsewhere in the corpus, just not inside this particular chapter. Widened search
  corpus-wide once this was understood.

**Prompt builder, four real revisions in one day**, each driven by direct user review of the
actual prompt text:
- **v1**: draft prompts for 3 sample units. Reviewed and found wanting: duplicated XML tags,
  glossary too weak, no real entity identification.
- **v2**: switched to a real model call for entity identification (per the user's instruction),
  plus a classical dictionary of proper names (added to the repo by the user) as the primary
  entity source, with embedding-based sense disambiguation for names with multiple entries.
  Real disambiguation bugs found and fixed: a "true redirect" vs. a "see-also footnote" treated
  the same; the dictionary's own index hitting the identical fold-collision bug one layer up; an
  override rule dropped after it incorrectly overrode a correct top score; a generic group noun
  matching an obscure historical minister since the dictionary only covers proper names.
- **v3**: the extraction step was only finding entities central to the root narrative, missing
  the commentary's own incidental illustrative figures. Fixed the extraction instruction to read
  all three text blocks equally — one unit's entity count went from 8 to 35. This surfaced a
  real bug: the richer extraction made responses longer, the output-token cap cut one unit's
  JSON mid-array, and the parse failure was silently cached as "0 entities" — stayed broken even
  after raising the cap, since the cache short-circuited the retry. Fixed the cap and stopped
  caching parse failures as results. Added a semantic-search fallback (via the benchmark-winning
  embedding model) as a third source after the dictionary and exact citation. Rebuilt the output
  format to 9 mandatory sections, kept as flowing prose rather than bullet lists.
- **v4**: two more fixes from direct review. (1) Storyteller rules now explicitly forbid naming
  internal sources in the output text — cards still record their source for the writing model's
  own grounding, instructed to stay invisible to the reader. (2) Built a related-content search
  to pull in related root text and commentary from elsewhere in the whole book, with a hard
  no-spoiler rule enforced at retrieval (a hit from the same chapter is only included if its
  unit comes at or before the one being explained — later content is never in the corpus a unit
  can draw from, not left to the model to self-censor). This also caught a real pre-existing
  spoiler bug in the embedding fallback.

**Full introduction ledger built** — the pilot samples had hard-coded "every entity is a first
appearance," correct only in isolation. Real version walks all 149 units in order with a shared,
mutating seen-entities set, correctly marking full introductions vs. brief reminders.

**Real performance bug found and fixed just before the full run.** First timing test: 73-186
seconds per unit — at that rate, 149 units would take 3-7+ hours. Root cause: the entity-card
builder was re-embedding the same unit context once per entity (20-35 entities/unit after the
v3 thoroughness fix) instead of once per unit, and calling an uncached full-corpus search for
every entity not resolved by the dictionary, every single time. Fixed both: the context
embedding is now computed once per unit and reused; a canon-wide fold index is built once per
process and reused for every entity in every unit. Post-fix: roughly **10-20x faster**.

**Real pricing verified live** (not recalled, since the model postdates training data), fetched
directly from the provider's own pricing page.

**Full 149-unit prompt-build, started ~17:47, finished.** Real Stage 6 ledger, per-unit timing,
full JSON-lines logging, every unit's prompt and metadata written to disk. **149/149 built
successfully, zero failures.** 3,233.7s total (53.9 min), 21.7s/unit average (2.6-87.1s range).
Real input tokens: 808,843 total, 5,428/unit average — exact, not estimated. Output tokens are
