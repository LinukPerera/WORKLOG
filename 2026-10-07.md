## Tikka translation process — n-gram mapper table + S0101 experiment — 1.5 hours

Source: `Tikka_translation_process/WORKLOG.MD`

Two parts: (1) the Tikka n-gram mapper table, built and wired into this
repo, and (2) a separate root-translation experiment that uses it, built in
its own folder outside any git repo (it holds live third-party API keys).

### Part 1 — Tikka sentence n-gram / example mapper table

**Problem:** the existing table-TM dry run (`translation_service_sub_commentary_dryrun_table_tm.py`)
had to rebuild a full n-gram index from `project_tm_examples` on every run
(minutes of index-build time) before it could find `<examples>` for any
Tikka sentence.

**Built:**
- `sentence_ngram_mapping_table.py` — three new Postgres tables
  (`"PaliVerse".sentence_ngram_map`, `sentence_translations`,
  `sentence_examples`) plus two views (`v_sentence_examples_with_text`,
  `v_exact_match_substitutions`). One row per unique Pali sentence, storing
  its n-grams once, whether it has a translation, and (for Tikka sentences)
  its precomputed best-matching examples — exact matches (verbatim Pali
  text found elsewhere, ready for direct substitution) ranked ahead of
  n-gram matches. Normalized so adding a new language later is just new
  `sentence_translations` rows, no schema change.
- Populated for the full corpus: 298,385 distinct Tikka sentences against
  all 558,739 translated root_text/commentary pairs. Run time 6.7 minutes.
  Results: 13,250 (4.4%) exact matches, 285,135 n-gram-matched (188,820
  with ≥1 example, 96,315 with none).
- Found and fixed a real bug during this run: 1,729 sentences that were
  both a Tikka line and (coincidentally) an already-seen example elsewhere
  got stuck mislabeled `text_type='commentary'` with no `file_source`/
  `xml_id` — an `ON CONFLICT DO UPDATE` wasn't overwriting those identity
  columns. Corrected the existing rows and patched the insert to always
  let the Tikka pass win identity fields on conflict.
- `translation_service_sub_commentary_dryrun_sentence_table.py` — new dry
  run variant that reads `<examples>` straight from the mapper table
  (via `sentence_ngram_mapping_table.fetch_examples_for_segments` /
  `attach_table_backed_examples`) instead of running `SegmentExampleFinder`
  live. Verified against real generated output: exact matches (e.g. the
  `Namo tassa...` invocation) correctly return only their one true match,
  not diluted with n-gram noise; ran in 27.6s vs. several minutes before.

### Part 2 — S0101 Chapter 1, four-AI root-translation experiment

Separate folder: `/home/linuk/experiment_s0101_four_ai/` — deliberately
**not** a git repo, since it holds four live third-party API keys
(`secrets/api_keys.yaml`, `chmod 600`, gitignored). Full method, function
reference, and real sample prompt data are recorded in that folder's own
`DOCUMENTATION.md`. Dry-run / cost-estimate stage only — no translation API
has been called.

**Key correction:** the key supplied as "Claude" was actually a DeepSeek
key (matched an existing `deepseek:` config block already committed in
this org's `translation_process` repo history, commit `59de896`). Real
Anthropic key retrieved from the mistranslation-finder webapp's own key
file, verified `sk-ant-api03-...` format, confirmed live.

**Pricing researched** (web search, since all four current models post-date
this session's knowledge cutoff): Claude Opus 5.5 ($4/$20 per MTok), Kimi
K3 ($3/$15), OpenAI GPT-6 Astra ($10/$50 standard tier). Meta has
discontinued Llama for a new closed model (Muse Spark) that's
private-preview only with no published pricing — modeled as `unknown`,
not assumed free.

**Leak-free test dataset (`test_dataset_loader.py`):** root text is ~89%
already translated in production, so Chapter 1's own sentences are mostly
already inside `project_tm_examples` — matching them normally would hand
back their own existing translation as a "perfect example." Fixed by
excluding every Chapter-1 sentence's exact Pali text from the TM index
before matching, and storing the real existing translation only in a
hidden `reference_translation` column (for scoring later, never shown to
a model). A second leak was found during verification — short/generic
segments colliding by `pali_hash` with unrelated rows from Part 1's run —
fixed by excluding non-substantive (bare verse-number) segments and adding
a defensive scrub of any pre-existing associations before relabelling a
row `dataset='test'`. Verified zero leaked translations and zero
self-matched examples across all 460 real test sentences.

**Root-context resolver (`root_context_resolver.py`):** a root unit has no
stored forward link to its commentary, so this does the reverse lookup —
root → commentary via `main_file`/`main_unit_id` on the commentary's bold
row, then commentary → sub-commentary via `comment_file`/`comment_unit_id`
on the Tikka bold row. Verified against real data for `s0101m.mul` ch.1.

**Prompt assembly (`dry_run_experiment.py`):** built all 149 Chapter-1
prompts using `Prompt for English.txt`'s tag format
(`<to_translate>`, `<reference>`, `<lemmatised_text_to_translate>`,
`<lexicon>`, `<examples>`), plus an appended `<subcommentary>` tag for the
Tikka context. **Commentary context is Pali-only** — deliberately changed
after review, since showing the (unevenly available) English commentary
would hand the model a human translation of adjacent material, biasing
the comparison between the four providers. Claude's input-token counts are
real (`anthropic.Anthropic.messages.count_tokens`, free, no completion);
the other three use a `tiktoken` proxy tokenizer, flagged as approximate.

**Bug found and fixed while documenting:** `fetch_lemmatised` joined on
`pali_data_review.stemmed_text`, which is `NULL` for this corpus — every
`<lemmatised_text_to_translate>` entry was silently empty. Fixed to the
correct column, `stemmed_llm_text_clean`, and the full 149-prompt dry run
was regenerated.

## LogPrompts Research (Alpha-Log-Probs) — 2.5 hours

**Summary:** Designed a way to use the AI's confidence in a translation to
decide which translations need human review.

Tasks:
- Defined the workflow: high-confidence translations pass automatically,
  low-confidence ones go to a human editor.
- Compared three ways of measuring confidence.
- Outlined the technical design for collecting the confidence scores.
- Added a safeguard so a score is never matched with text that was edited
  later.
- Planned testing against benchmark data and past human edits to confirm
  real errors are caught without false alarms.
