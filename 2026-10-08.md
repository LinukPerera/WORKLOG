**Round 1 — server-side CORS/endpoint probing (via curl):**
1. Unauthenticated `GET` to `stage.paliverse.org/wp-json/webst/v1/user-access`
   → `200`, `{"logged_in":false,"allowed":false,"user":null}`.

   headers. Conclusion: CORS was fine on the main check endpoint.
4. Checked `/wp-json/` root discovery on both `stage.paliverse.org` and

   suggesting separate WordPress installs.
5. Confirmed the `webst/v1/user-access` endpoint also exists on
   production, same unauthenticated response shape.
6. Hypothesis formed: stage and production are separate logins —
   explains the redirect if the user logged into production only.

**Round 2 — building server-side diagnostic tooling (since only the
browser has the real session):**
7. Added `logDebug()` in `static/auth-gate.js` to POST the raw WordPress
   response to a new backend endpoint before deciding pass/fail, plus a
   new `POST /api/auth/debug-log` route in `server.py` that appends to a
   local gitignored log file.
8. First real-login test after deploying this → nothing was logged at all.
9. Diagnosed why: the debug-log fetch was being cancelled by the
   browser's redirect (`window.location.replace()`) before it finished.

10. Redeployed, retested → still nothing logged.
11. Tested the debug-log endpoint directly via curl to isolate frontend

    the app's own `output/`, `data/`, `keys/` — had been broken since
    go-live (audit trail, saved searches, write-back backups, lemma
    rebuild all silently failing). Fixed by adding `ReadWritePaths=` to
    the systemd unit, service restarted.
13. Retested the debug-log endpoint via curl → confirmed working now.
14. User logged in again (three attempts) → captured real data each
    time: `{"nonce_sent": false, "http_status": 200, "body":
    {"logged_in": false, "allowed": false, "user": null}}` — confirming
    no network/CORS error, just a clean "not logged in" from stage,
    consistent with the separate-login hypothesis.

## LogPrompts Research (Alpha-Log-Probs) — project scaffolding — 3 hours (15:30–18:30)

Source: `Alpha-Log-Probs/worklog.md`

Set up the feasibility study asking: do logprob-based signals from
[`logprobs-mt-qe`](https://github.com/inacioinvita/logprobs-mt-qe) actually predict machine
translation quality well enough to be useful? This repo's own two existing docs
(`LOGPROBS_Shindan.md`, `LOGPROBS_GENERATION_CONFIDENCE.md`) already show Intertranslations'
own prior test of a similar approach only reached AUC 0.39–0.56 against real human post-edits —
barely better than chance, and worse than an LLM-judge baseline (0.57–0.72) on the same segments.
This study re-runs that calibration properly on a public benchmark, and checks whether
`logprobs-mt-qe`'s richer distributional signals (`composite_score`, `weak_share`, uncertain
spans) do any better than the plain `mean_logprob` Shindan already tried. Uses only publicly
available datasets throughout.

### What was done

- Cloned this repo (`LinukPerera/Alpha-Log-Probs`) and vendored a flat copy of
  `inacioinvita/logprobs-mt-qe` into `external/logprobs-mt-qe/`, with the exact commit SHA
  pinned in `external/logprobs-mt-qe/VENDORED_FROM.md` for provenance. Chose a plain vendored
  copy over a git submodule — the goal is to import and call the existing code directly, not
  track upstream closely, and a flat copy is simpler for anyone else cloning this repo.
- Installed `uv` and set up the project (`pyproject.toml`, `uv.lock`) with `datasets`,
  `huggingface_hub`, `pandas`, `numpy`, `scipy`, `matplotlib`, `pytest`.
- Verified the vendoring didn't break anything: ran the three offline demos
  `logprobs-mt-qe` itself documents as "known-good" (`demos/mt/translate_with_confidence.py`,
  `demos/qe/rank_candidates.py`, `demos/qe/agreement.py`) — all ran clean with zero server
  dependency. Deliberately did **not** rely on the other five QE demos or `QElogprob.json`,
  which are the repo's own documented, unfixed alignment-gap bugs.
- Found and confirmed a real, public dataset for the benchmark arm:
  `RicardoRei/wmt-mqm-human-evaluation` on Hugging Face (Apache-2.0, no auth needed,
  150k+ rows of `src`/`mt`/`ref`/continuous MQM `score` across WMT years and language pairs).
  Wrote `scripts/download_public_dataset.py` and downloaded a pilot slice (`en-de`, 2022,
  19,725 labeled segments) to `data/public/wmt_mqm/en-de_2022.csv`.
- Worked out a key technical wrinkle in `logprobs-mt-qe` itself: its generation-mode path
  (`mt/translate.py`) always has the model produce a *fresh* translation — there's no way to
  force it to "generate" text someone else already wrote, so it can't directly score an
  existing MT/post-edit pair. Fixed this with a small adapter rather than reimplementing
  anything: `qe/score_live.py`'s teacher-forced `score_hypothesis()` already returns per-token
  `positions`, and `qe/lib_prompt_logprobs.py`'s `top_logprobs_from_position()` gives exactly the
  shape needed to feed `mt/lib_mt_confidence.py`'s richer distributional functions
  (`content_token_summary`, `find_uncertain_spans`) from the *same* API call.
- Wrote `scripts/qe_adapter.py` (the bridge above) and `scripts/evaluate.py` (`confusion()` and
  `auc()` ported near-verbatim from `LOGPROBS_Shindan.md` §8, so results are directly comparable
  to Shindan's own prior numbers). Both are unit-tested with no live backend required —
  `evaluate.py`'s tests regression-check against the exact batch-21 worked numbers in that doc
  (TP 70 / FP 564 / FN 27 / TN 235 → precision 0.11, recall 0.72).
- Wrote the backend-agnostic batch scoring scripts — `scripts/score_segments_qe.py` (plain
  teacher-forced aggregates, the exact signal family Shindan already tested) and
  `scripts/score_segments_mt_distributional.py` (the untested richer signal family) — plus
  `scripts/smoke_test.py`, which reproduces the three-sentence-version sanity check from
  `LOGPROBS_Shindan.md` §10 (correct / meaning-error / untranslated) to run once a backend is
  chosen, before trusting any full dataset run.
- Set up `.gitignore` so large/regenerable files (the public dataset cache, raw results dumps)
  stay out of commits by default.
- 11/11 `pytest tests/` pass without any live backend.
- Committed all of the above to this repo (commit `c8bb8d0`).

## PaliVerse — aicorrector.paliverse.org go-live — 2 hours (18:30–20:30)

Source: `paliverse_mistranslations_finder_webapp/WORKLOG.md`

**Round 6 — WebST proposed a redirect-based SSO flow instead:**
1. WebST replied: the Python app has no WordPress username/Application
   Password, so a purely server-to-server check was never possible —
   the session only exists in the visitor's browser. They proposed an
   OAuth-style authorization-code redirect flow instead (no nonce, no
   cookie sharing, no CORS needed at all) and asked for our callback
   URL(s).
2. Assessed it as a better design than our own proposed fix — properly
   solves every blocker found, and is more secure (the API key would
   never reach browser JavaScript). Recommended adopting it.
3. Replied confirming the production callback URL
   (`https://aicorrector.paliverse.org/api/auth/callback`), noted we
   have no staging deployment so staging is not applicable, and asked
   WebST to send the full implementation details (authorize URL +
   params, code-exchange endpoint + request/response shape, how our
   backend authenticates itself, and the not-logged-in/not-permitted
   behavior) once ready.

**Round 7 — WebST delivered the full spec; implemented and deployed:**
4. WebST sent the complete flow: authorize URL
   (`www.paliverse.org/wp-admin/admin-post.php?action=webst_python_app_authorize`)
   with `state` + PKCE `code_challenge` (S256); callback receives
   `code`/`state` (or `error`); code exchanged server-to-server via
   `POST www.paliverse.org/wp-json/webst/v1/python-auth/exchange` with
   `{code, code_verifier}`, returning user identity and a per-session
   Segment API `{base_url, header_name, api_key}`.
5. Implemented it: rewrote `engine/auth_gate.py` with the PKCE/state
   helpers and `exchange_code()`; `server.py`'s `index()` now redirects
   to WordPress when ungated instead of serving a shell; added
   `GET /api/auth/callback` validating state then exchanging the code;
   `GateState` extended with the dynamic segment API fields.
   `engine/segment_api.py`'s `SegmentApiConfig` gained a `header_name`
   field (WordPress returns it dynamically now, not a fixed constant).
   `engine/apiwriteback.py`'s `apply()` now takes the full dynamic
   `SegmentApiConfig` instead of just an `api_key`.
6. Removed entirely, now unnecessary: `static/auth-gate.js` (no more
   browser-side WordPress calls at all), the `/api/auth/establish`
   route (a real, if minor, trust gap in the old design — it accepted
   whatever `api_key` the browser posted with no independent
   verification; the new callback route is the only way `GateState`
   ever gets set, and only as the result of a verified exchange), and
   the temporary `/api/auth/debug-log`/`debug-cookies` diagnostic
   routes (their job — finding this root cause — is done).
7. Tested locally on an isolated port before touching production:
   confirmed `/` redirects to the real WordPress authorize URL with
   correct `state`/PKCE params, `/api/bootstrap` stays gated, and the
   callback route fails closed cleanly (no exceptions) on missing
   state, mismatched state, and a rejected fake code.
8. Deployed to production (service restart). Re-verified live: the
   real redirect URL, the gate still blocking `/api/*`, and the old
   `establish`/`debug-*` routes no longer functioning.
9. Rewrote `OPERATIONS.md` §3 to document the new flow in full and
   moved the old cookie+nonce design to a "history" subsection for
   context on why the architecture looks the way it does.
10. Status: deployed and verified for all the redirect/fail-closed
    paths. **Not yet verified: an actual successful login** — needs a
    real browser + permitted WordPress account to complete the full
    round trip. Next step: just try it.

**Round 8 — a "staged" write landed in production; found, fixed, verified:**
1. User reported that applying a correction in Staged DB mode actually
   wrote to the live production database instead.
2. Found the exact evidence on disk:
   `output/writeback_backups/writeback_backup_20261008_142600.json` —
   English segment id `36949383` (`abh01a.att`, xml_id `3537`), "community
   of monks" capitalized to "Community of monks". The backup's own
   `target` field incorrectly said `stage.paliverse.org` (that field is
   generated from the plan's label, not the real URL used), so even the
   saved record didn't reveal the mistake at a glance.
3. Root cause: `/api/writeback/apply` in `server.py` built the
   `SegmentApiConfig` from the session's `GateState` unconditionally,
   regardless of whether the write was "staged" or "production". Since
   `GateState` only ever holds the production-scoped credential from the
   OAuth exchange (WebST's flow has no per-user auth for staging at all),
   every write — staged or production — silently used production's URL
   and key.
4. Fixed in two places: `server.py` now branches on `kind` — production
   uses the per-user OAuth credential; staged falls back to the static
   shared key from `config.yaml`'s `segment_api.stage` block (the
   pre-OAuth mechanism, still intact). Added a second, independent
   safety net in `engine/apiwriteback.py`'s `apply()`: it now checks
   that the resolved URL's hostname actually matches what `self.kind`
   expects (`stage.paliverse.org` vs `www.paliverse.org`) and refuses
   to send anything — before any network call — if they don't match.
5. Verified with a mocked Segment API call for both the exact bug
   scenario (staged plan + production URL → refused, zero network
   calls made) and the correct case (staged plan + stage URL →
   proceeds normally).
6. Deployed (service restart), re-verified the live gate still works
   with no regression.
7. Documented in `OPERATIONS.md` §3.7 as a named past incident, with
   the evidence, root cause, fix, and an explicit note on what wasn't
   done: the live production edit itself was not reverted (minor,
   plausibly-correct change; reverting is a content judgment call, not
   an automatic part of a bug fix).
8. Also clarified for the record: per-user API key attribution (the
   key from the WordPress JSON exchange) now correctly applies **only**
   to production writes, which is the only environment WebST's OAuth
   system covers. Staged writes necessarily use the shared static key
   and lose per-user attribution — there is no WebST-side mechanism for
   per-user staging auth today.
